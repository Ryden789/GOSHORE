# GOSHORE 工作细则

> 本文件是本仓库所有开发工作的**流程宪法**。任何 AI 工具、任何协作者、任何阶段的改动，均须先读本文与 [开发任务手册](03-开发/开发任务手册.md)，再动手。
> 与本文冲突的其他约定，一律以本文为准；确需例外，走 §12 例外流程。

| 项 | 内容 |
|---|---|
| 文档编号 | RULE-001 |
| 版本 | v1.0 |
| 生效日期 | 2026-10-30 |
| 适用范围 | 本仓库全部代码、数据、文档、发布物 |
| 状态 | **已生效** |

---

## 1. 第一原则：无文档不开工

**任何工作开始前，必须先创建该任务的工作文档；文档不存在时，禁止写第一行代码、禁止改第一个文件、禁止跑第一次迁移。**

顺序是硬性的：

```
① 建任务文档  →  ② 填写 §2 模板的六节  →  ③ 自检 6 问（§3）
   →  ④ 开工  →  ⑤ 边做边追加留痕  →  ⑥ 按验收标准判定
```

### 1.1 什么算「工作」

以下任一动作即触发本条：

- 新增或修改 `app/`、`static/`、`tools/`、`android/` 下的任何文件
- 变更数据库结构、迁移、批量重导入
- 变更 CI、构建、依赖
- 引入第三方代码或数据（含开源项目借鉴）
- 对外发布（Release、APK、宣传材料、毕设材料）

以下不算：修正错别字、仅调整文档措辞、纯查询（读代码/跑统计）。

### 1.2 任务文档的落盘规则

| 项 | 规定 |
|---|---|
| 位置 | `docs/03-开发/` |
| 命名 | `YYYY-MM-DD-<任务名>.md`，同一天多任务加后缀 `-A` / `-B` |
| 例外 | 属于产品定义 → `docs/01-产品/`；属于设计 → `docs/02-设计/`；属于评审 → `docs/04-评审/` |
| 长任务 | 超过 1 个工作日的工作，文档内必须维护「任务台账」（§6.1），逐日追加 |

## 2. 任务文档必备六节

缺任一节的任务文档视为**未完成**，不得开工。
六节之上还有**排版与写法要求**（命名、元信息表、动词口径、表格、引用、版本），一律遵照 [文档规范](文档规范.md) 执行；本文只规定「写哪些」，DOC-001 规定「怎么写」。

### §A 目标与边界

- 要做什么（编号 G1、G2…，每条配判定方式）
- **明确不做什么**（防范围蔓延，列出被排除的相邻工作及理由）

### §B 现状核对（实测）

- 涉及的文件、行号、接口、表结构，必须写出**实测结果**而非印象
- 格式：`项 | 实测结果 | 影响`
- 禁止出现「应该是」「我记得」「一般来说」

### §C 方案与取舍

- 选定方案 + **被否方案及否决理由**
- 若涉及外部项目/数据，写明许可与来源

### §D 执行步骤

- 阶段划分（P0、P1…），每阶段写前置条件、产物、状态
- 顺序依赖必须显式写出（「X 必须在 Y 之前，因为……」）

### §E 验收标准

- 每条可量化、可复跑、可被他人验证
- 至少包含一条「防倒退」项（如误替换数 = 0、重导后零漂移）

### §F 留痕与回滚

- 证据文件路径（日志、报告、CSV）
- 回滚方式（如何撤销、影响范围）

## 3. 开工前自检 6 问

逐条回答，答不出就不开工：

1. 这个任务的工作文档建了吗？路径是什么？
2. §B 的现状核对是**实测**还是推测？证据在哪？
3. 验收标准能被别人复跑吗？
4. 失败时怎么回滚？影响哪些既有数据？
5. 有没有引入第三方代码/数据？许可登记了吗？
6. 这次改动会不会碰到 `qid`、许可、题库分发这三条敏感线？

---

## 4. 实测优先：禁止凭记忆写代码

**凡涉及第三方库、API、数据结构的调用，必须先写探针脚本并贴出真实返回结构，再写封装。**

| 场景 | 强制动作 |
|---|---|
| 第三方库版本跨大版本 | 写 `probe_*.py`，打印真实调用方式与返回对象 |
| 数据库表结构 | 直接查 `sqlite_master` 与实测行数，不引用旧文档 |
| 数据规模/覆盖率 | 跑 SQL 统计，把数字写进文档 §B |
| 外部项目能力 | 拉取源码或文档确认，不凭项目名推断 |

违反本条导致的返工，不计入工时，视为流程违规。

## 5. 留痕规则

### 5.1 五条纪律

1. **只追加，不覆盖**：历史记录一律保留；修正时新增一行并注明「修正原第 X 行」。
2. **每个结论都要指到文件**：任何「提升了 / 降低了 / 修好了」的表述，必须附证据文件名。
3. **失败也要留痕**：报错、加载失败、指标低于预期，同样记入台账，不得略过。
4. **口径写死在代码里**：指标定义（如 CER、准确率）只允许在代码中定义一次，文档与报告引用同一口径。
5. **时间戳真实**：记录使用实际执行时间，不写估算时间。

### 5.2 三类必备台账

| 台账 | 位置 | 追加时机 |
|---|---|---|
| 任务台账 | 任务文档内 | 每完成一个阶段 |
| 运行记录 | 任务文档内或 `logs/` | 每次批量执行 / 每次评测 |
| 变更日志 | 任务文档内 | 每次改口径、改词表、改表结构 |

### 5.3 状态三态

全仓统一使用：

| 状态 | 含义 | 允许的对外表述 |
|---|---|---|
| 未开始 | 只有计划 | 只能说「拟做」 |
| 进行中 | 有代码或数据但未达标 | 只能说「在做，未达标」 |
| 已验收 | 通过 §E 验收标准 | 才可写入毕设、简历、宣传材料 |

**未验收的内容出现在对外材料中，视为严重违规。**

## 6. 改动边界

| 规则 | 说明 |
|---|---|
| 最小改动 | 只改与本任务直接相关的代码；不顺手重构、不顺手格式化 |
| 不动无关文件 | 不修别人遗留的风格问题、不改无关命名 |
| 不删既有能力 | 删除公开函数/字段/端点前，必须在 §C 写明影响面与替代方案 |
| 不做兼容垫片 | 不留「为兼容而保留」的死代码；确定不用就删干净 |
| 不隐性补齐 | 数据缺失不得用默认值悄悄填平，必须显式报告缺失清单 |

---

## 7. 三条敏感线（触碰即升级）

| 敏感线 | 要求 |
|---|---|
| **qid（稳定题号）** | 任何影响题目主键的改动，必须附「重导入两次，`due_at`/`stage`/`mastery.score`/`answers` 行数零变化」的验证结果 |
| **许可** | 引入第三方代码或数据，须在 [来源与许可登记](来源与许可登记.md) 追加一行；GPL 类只进 `reference_only/`，并由 `tools/check_license_guard.py` 在 CI 拦截 |
| **题库分发** | 分片/索引/懒加载相关改动，必须验证冷启动可用性与包体积变化 |

---

## 8. Git 与提交纪律

1. **一次提交只做一件事**：文档与代码可分开提交，但二者必须能互相指认（commit message 引用任务文档名）。
2. **commit message 写「为什么」**，不写「改了什么」。
3. **禁止** `push --force`、`reset --hard`、`checkout --` 等破坏性操作，除非在任务文档 §F 明确声明并获批。
4. **不提交**密钥、`.env`、大体积题库原始文件、`reference_only/`。
5. 提交前必须跑：`pytest`、`python tools/check_license_guard.py`。

任务完成后文档**不移除、不改名**，作为历史证据保留。

## 10. 对外表述的硬约束

写毕设、简历、宣传、演示文稿时：

| 允许 | 禁止 |
|---|---|
| 「拟提出 / 拟实现 / 预期达到」 | 「已完成 / 已实测 / 已验证」（未验收时） |
| 「在 N 份样本上观测到 X」并附样本说明 | 「显著提升 / 大幅改善」等无数值表述 |
| 「该方法假设……其局限是……」 | 隐去样本量、单书写者、单一考试类型等限制 |

任何数字必须可在仓库内找到出处（`logs/`、报告文件、SQL 输出）。

## 11. 工具与协作者的接入要求

任何 AI 工具或协作者进入本仓库，第一步必须：

1. 读本文件、[文档规范](文档规范.md) 与 [开发任务手册](03-开发/开发任务手册.md)；
2. 在本次任务文档开头写明「本任务遵守 RULE-001 v1.0 与 DOC-001 v1.0」；
3. 若发现本次工作与细则冲突，**先停下来写到文档 §C**，不得擅自变通。

---

## 12. 例外流程（紧急热修）

线上故障、数据损坏等确需先动手的情况：

1. 先在 `docs/03-开发/` 建一份**一句话**的临时文档（说明故障与止血手段）；
2. 止血；
3. **24 小时内**补齐 §2 六节，并把临时文档标记为「已补齐」；
4. 未补齐者，该改动视为未验收，不得进入 Release 说明。

---

## 13. 违规判定

| 情形 | 判定 |
|---|---|
| 无文档开工 | 流程违规，改动不计入成果 |
| 未验收即写入对外材料 | 严重违规，须撤回相关材料 |
| 结论无证据文件 | 视为未完成 |
| 凭记忆写 API 导致返工 | 流程违规，返工不计工时 |
| 隐性补齐缺失数据 | 严重违规，须显式标注缺失清单 |
