# GOSHORE 文档规范

> 本文件规定**文档怎么生成**；[工作细则](工作细则.md) 规定**工作怎么开展**。二者分工明确：
> 工作细则回答「要不要写文档」，本文件回答「文档写成什么样」。
> 两者同时生效，缺一不可。

| 项 | 内容 |
|---|---|
| 文档编号 | DOC-001 |
| 版本 | v1.0 |
| 生效日期 | 2026-10-30 |
| 适用范围 | `docs/` 目录下全部 Markdown 文件，以及仓库内任何对外交付的 md |
| 状态 | **已生效** |

---

## 1. 文档类型决定一切

先定类型，再套模板。类型错了，后面全错。

| 类型 | 目录 | 命名 | 是否带日期 | 生命周期 |
|---|---|---|---|---|
| 常驻规则 | `docs/` 根 | `工作细则.md` / `文档规范.md` | 否 | 长期有效，版本迭代 |
| 任务文档 | `docs/03-开发/` | `YYYY-MM-DD-<任务名>.md` | 是 | 完成后保留，不改名 |
| 产品/需求 | `docs/01-产品/` | 中文名 | 否 | 随产品演进更新 |
| 设计 | `docs/02-设计/` | 中文名 | 否 | 随实现演进更新 |
| 评审 | `docs/04-评审/` | `YYYY-MM-DD-<主题>.md` | 是 | 一次性，不二次编辑 |
| 发布记录 | `docs/03-开发/Release历史/` | `E<n>-YYYY-MM-DD.md` 或 `vYYYY.MM.DD.md` | 是 | 只追加 |
| 宣传/对外 | `docs/05-宣传/` | 中文名 | 否 | 受工作细则 §10 约束 |

**判定问句**：这份文档是用来「约束将来的工作」还是「记录已发生的工作」？
- 约束将来 → 常驻规则 / 产品 / 设计
- 记录已发生 → 任务 / 评审 / 发布

---

## 2. 文件命名硬规则

1. 文件名用中文时**不加空格**，用 `-` 连接语义块：`2026-10-30-申论手写OCR评测集与词表纠错方案.md`
2. 日期一律 `YYYY-MM-DD` 前缀，**不写 `20261030`、不写 `10-30`**
3. 任务名内不含版本号（版本写在文件内，不写在文件名里）
4. 同一天多任务，按创建顺序加后缀 `-A`、`-B`，不加 `-1`、`-2`
5. 禁止在文件名中出现：`最终`、`最新`、`修改版`、`new`、`副本`
6. 一次任务对应一个文件；**禁止**把多个任务塞进一个文档

---

## 3. 头部元信息表（常驻规则与任务文档必备）

文件标题（`#`）之后**紧跟**一张两列元信息表，缺字段视为不合规：

| 字段 | 必填 | 说明 |
|---|---|---|
| 文档编号 | 常驻规则必填 | 形如 `RULE-001` / `DOC-001` / `OCR-001`；任务文档可自拟 |
| 版本 | 是 | `v1.0` 起步，见 §9 |
| 生效/撰写日期 | 是 | `YYYY-MM-DD` |
| 适用范围 | 是 | 约束对象或任务边界 |
| 状态 | 是 | `待评审` / `已生效` / `未开始` / `进行中` / `已验收` |

任务文档允许用「目标 / 面向场景 / 落盘位置」等字段替换，但**状态字段不可省**。

---

## 4. 章节结构规范

1. **全文只有一个一级标题 `#`**，即文档名
2. 二级标题用阿拉伯数字：`## 1. xxx`；三级：`### 1.1 xxx`
3. 层级不超过三级；需要第四级时改用列表或表格，不再加 `####`
4. 编号连续不跳号；新增章节时在文末追加，**不重排已有编号**（因为其他地方可能引用「§7」）
5. 引用其他章节统一写「§N」或「§N.M」，不写「见上文」
6. 常驻规则类文档必须有「变更日志」且在文末

---

## 5. 语言规范（最容易违规的部分）

### 5.1 动词口径

| 场景 | 必须用 | 禁止用 |
|---|---|---|
| 计划、未开工 | 拟、预期、计划 | 已完成、已实现、已验证 |
| 有代码未达标 | 在做、尚未达标 | 基本完成、差不多了 |
| 已通过验收 | 已验收、实测结果为 | — |
| 描述方案 | 拟采用、选定 | 已经用了 |

### 5.2 数字必须有出处

- 禁止裸形容词：「显著提升」「大幅改善」「效果很好」「性能优秀」
- 正确写法：`在 20 份样本上，字准确率由 87.3% 提升至 91.6%（`logs/eval_20261030.json`）`
- 任何数字必须能在仓库内找到对应证据文件

### 5.3 限制必须自己说出来

涉及实证结论时，必须写明：样本量、样本来源、单一性限制（如「单书写者」「仅省考卷」「不含国考卷」）。
**主动声明局限比被问出来强。**

### 5.4 排版细则

| 项 | 规定 |
|---|---|
| 中英文之间 | 加一个半角空格：`用 Python 跑 pytest` |
| 标点 | 正文用全角，代码与路径用半角 |
| 引号 | 中文内容用「」，不用 "" |
| 省略号 | 用 `…`，不用 `...` |
| 强调 | 用 `**加粗**`；不用 `*斜体*`（中文斜体难读） |
| emoji | 禁止出现在任何文档 |
| 空格缩进 | 不用空格做层级缩进，用列表或表格 |

---

## 6. 表格规范

1. **每张表都要有表头**，且表头字段名具体（写「实测结果」不写「情况」）
2. 表格列数 ≤ 6；超过则拆表
3. 表格上方一句引导语说明这张表回答什么问题
4. 单元格内不换行、不塞长段落；内容超 40 字改为列表
5. 空值写 `—`，不写空格、不写 `无`（`无` 表明确认过不存在，`—` 表未涉及）
6. 状态列只用三态词：`未开始` / `进行中` / `已验收`

---

## 7. 代码与路径引用规范

1. 代码块**必须带语言标签**：```python、```sql、```json、```markdown
2. 引用仓库内文件用相对路径的可点击链接，不写裸路径文本
3. 引用具体位置时写明行号范围，并说明这段代码的作用
4. 大段代码（> 30 行）不贴入文档，改为说明「函数名 + 文件 + 行为」并给出定位链接
5. 目录树用 ```text 代码块，字符用 `├─`、`└─`，不用 `|-`

---

## 8. 留痕写法（与工作细则 §5 对接）

### 8.1 台账表格式（固定三列不得改）

| 日期 | 任务 | 阶段 | 结果 | 证据文件 | 状态 |
|---|---|---|---|---|---|

- `结果` 列写**实测值**，不写「完成」
- `证据文件` 列必须是可打开的路径，无证据则填 `—` 且状态不得为 `已验收`

### 8.2 修正的写法

已有记录不删除。修正时**新增一行**并在结果列注明：`修正原第 3 行：…`

### 8.3 失败记录

失败同样入表，状态写 `未通过`，结果列写失败原因（如「paddleocr 权重下载超时」）。

---

## 9. 版本与变更日志

| 版本变化 | 触发条件 |
|---|---|
| v1.0 → v1.1 | 补充内容、修正表述，不改结论 |
| v1.0 → v2.0 | 改变核心方案、推翻既有结论、改验收标准 |

变更日志格式（文末，只追加）：

| 日期 | 版本 | 变更内容 |
|---|---|---|

规则：
- 不写「优化若干处」这类含糊表述，写具体改了哪一节
- 旧版本记录不删，即使内容已失效

---

## 10. 禁止事项（触犯即不合规，须重写）

1. 在未验收时使用「已完成 / 已实测 / 已验证」
2. 使用无数据的程度形容词（显著、大幅、良好、优秀）
3. 写「我估计 / 大概 / 应该是」而不标注为推测
4. 用裸路径文本代替可点击链接
5. 把多个任务合并进一份文档
6. 在文档中放假定的 API 或表结构而不标「待核对」
7. 删除历史台账行来「让文档变干净」
8. 文件名带「最终版」「修改版」
9. 章节号跳号或重排已有编号
10. 对未完成的方法使用「提出」「证明」等成熟学术动词

> 第 10 条最容易被忽略：**「拟提出」与「提出」是两个状态**，前者是本分，后者是虚报。

## 11. 提交前自检清单（10 项，逐条打勾）

- [ ] 类型与目录、文件名符合 §1、§2
- [ ] 头部元信息表齐全，状态字段已填
- [ ] 只有一个 `#`，章节编号连续无跳号
- [ ] 所有动词口径符合当前状态（拟 / 在做 / 已验收）
- [ ] 所有数字都有证据文件路径
- [ ] 所有实证结论都写明了样本量与限制
- [ ] 表格有表头、列数 ≤ 6、空值用 `—`
- [ ] 代码块都带语言标签；仓库文件都用链接引用
- [ ] 台账只追加未覆盖；失败记录已入表
- [ ] 文末有变更日志且写明具体改动
