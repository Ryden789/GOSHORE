### 与本地资源的关系

该仓库正是本地 `d:\人文\kaogongzhentizhengliu`（Obsidian vault，11,282 题）的**工程化版本上游**，README 中提到的原始 vault 与之同源。

### 结构


### 可借鉴点（本次调研最高价值的三条）

**1. SRS 以题库稳定题号 `qid` 为主键，而非自增 id**

引自其设计说明：`questions.id` 是自增主键、重导入时会变动；而 `srs` 表用题库自带稳定题号 `qid`（TEXT）作主键，因此**重新导入题库不会导致复习进度、笔记、收藏错位丢失**，并配有重导入对账逻辑。

> **对 GOSHORE 的直接意义**：检查现有复习队列与错题表是否以外键绑定自增 id。若题库重导或扩充（如接入 kaogong 11k 题），自增 id 漂移会导致复习记录串题。这是数据结构层面必须先定的决策。

**2. `sm2.py`（1.8KB）—— SM-2 复习引擎的纯函数实现**

四档评分（忘记 1 / 困难 3 / 一般 4 / 熟悉 5），纯函数 `grade_state()` 输入旧状态返回新间隔与到期日；附 `mastery_bucket()` 按 interval 分桶（学习中 / 初记 / 短期 / 长期 / 稳固）。

> **对 GOSHORE 的意义**：GOSHORE 现用 FSRS。该实现可作为**对照算法**纳入毕设实验（SM-2 vs FSRS 在同一错题库上的复习效率对比），是"方法验证"章节的低成本实验素材。

**3. `parse.py` —— Obsidian vault → SQLite 的导入器**

解析 frontmatter、`##`/`###` 小节、选项 ✅、答案兜底、图片路径归一化。

> **对 GOSHORE 的意义**：若要把本地 11,282 题 vault 接入 GOSHORE 题库，这是现成的解析思路；配合 `check_integrity.py` 的数据校验，可形成"导入 + 校验"闭环。

### 其他可借鉴

- **零第三方依赖交付**：后端仅用 `http.server` + `sqlite3` + `json` + `re`，理由是"pip 装不上是交付最大风险"。GOSHORE 桌面打包可对照评估依赖精简程度
- **分片数据库**：`kaogong.db.part-00~04`，与 kaogong-shuati 的 `tiku.db.part-*` 同一策略
- **图片自包含**：WebP 内置 + 路径归一化，运行时不再依赖原 vault
- **迁移脚本**：`migrate_v2.py` / `migrate_v3.py` 版本化迁移，可作为 GOSHORE 数据库演进参考

## 九、值得借鉴的具体做法（代码级细化）

以下每条都标注「借鉴来源 → 落地动作 → 改动位置 → 预估成本」，可直接作为开发任务单。

### 9.1 复习状态表改用稳定题号主键

- **来源**：GongkaoNaoku 设计说明（核心技术决策章节）
- **原文要点**：`questions.id` 为自增主键，重导入会变动；`srs` 表改以题库自带稳定题号 `qid`（TEXT）为主键，重导入后复习进度、笔记、收藏不会错位，并配重导入对账逻辑
- **落地动作**：
  1. 在题目表增加 `qid TEXT UNIQUE NOT NULL`，来源为题库自带编号；若无编号，则用「题干归一化后的内容指纹」（去空白、去标点、统一全半角后取哈希）生成
  2. 所有复习/错题/笔记/收藏表的外键改为绑定 `qid`，`questions.id` 降级为内部索引
  3. 补一个重导入对账函数：以 `qid` 为键做 upsert，统计「新增/更新/失联」三类数量并输出报告
- **改动位置**：`app/db.py`（表结构 + 迁移）、复习与错题写入路径、导入流程
- **预估成本**：表结构 + 迁移脚本约半天；写入路径改造约半天
- **风险**：若历史数据已按自增 id 绑定，迁移需一次性映射（用现有题库快照重建 qid → id 映射表）

> **2026-10-27 已核对 GOSHORE 实际代码，结论修正**：这条在 GOSHORE 里属于「**需迁移**」而非「新建」，涉及 9 张既有表 + 2 处 JSON 整数引用 + 1 处 id 生成逻辑，详见**第十四节**。好消息是 `qid` 字段和 `doc_id_by_qid` 转换函数已存在，可走「影子列双写」渐进迁移，不必一次改完 105 处 SQL。

### 9.2 补 SM-2 作为 FSRS 的对照实现

- **来源**：GongkaoNaoku `sm2.py`（1.8KB，纯函数）
- **算法要点**：四档评分（忘记 1 / 困难 3 / 一般 4 / 熟悉 5）；`grade < 3` 时重置 repetitions 与 interval 并累计 lapses；`reps == 1 → 1 天`、`reps == 2 → 6 天`、之后 `interval × ease × 系数`（困难 1.2 / 一般 1.0 / 熟悉 1.3）；ease 按 SM-2 公式更新且下限 1.3；另有 `mastery_bucket()` 按 interval 分为「学习中 / 初记 / 短期 / 长期 / 稳固」五档
- **落地动作**：独立实现为纯函数模块，与现有 FSRS 并列，用配置开关切换算法；`mastery_bucket` 可直接复用到驾驶舱的掌握度分布图
- **改动位置**：新增复习算法模块 + 调度入口一处分支
- **预估成本**：1 小时以内
- **额外价值**：可直接作为毕设「算法对比实验」的对照组，指标为同批错题的到期正确率与平均复习次数

### 9.3 Skill 工具链（校验 / 打包 / 审计）

- **来源**：xingce-review-pro `tools/` 四个脚本 + `.github/workflows/validate.yml`
- **四个脚本的分工**（按命名推断，需精读确认）：`validate_skill.py` 校验 SKILL.md 与 references 结构完整性；`package_skill.py` 打包为可分发产物；`audit_methods.py` 审计方法库覆盖度与重复；`normalize_cards.py` 卡片字段规范化
- **落地动作**：
  1. 为 GOSHORE 的申论 Skill 接入流程加一个校验入口：检查 SKILL.md 必填字段、references 引用路径是否存在、契约 schema 是否可解析
  2. 把校验挂进 CI，防止 skill 目录在后续改动中结构劣化
- **改动位置**：新增 `tools/` 目录 + CI 配置
- **预估成本**：半天
- **注意**：GPL-3.0 项目，**只借鉴分工设计，代码需自行实现**

### 9.4 复盘结论结构化回写

- **来源**：xingce-review-pro `scripts/writeback.py`（23.4KB）+ `references/protocols/data.md`（10.1KB）
- **价值**：把「复盘」定义为有明确输入输出协议的数据流，而不是页面上的一段文字；写回脚本负责落库
- **落地动作**：GOSHORE 已有 `essay_weak_points` 表，可对照其协议补一层：复盘结论 → 结构化字段 → 写入 → 驱动复习队列，并保留可追溯的原始来源
- **改动位置**：复盘模块输出层 + 写库路径
- **预估成本**：1 天
- **注意**：同样受 GPL 约束，参考协议设计即可

### 9.5 Obsidian vault → 题库导入器

- **来源**：GongkaoNaoku `parse.py` + `check_integrity.py` + `refill_images.py`
- **解析要点**：frontmatter 字段解析 → `##`/`###` 小节切分 → 选项「✅」标记识别 → 答案缺失时的兜底策略 → 图片路径归一化 → 导入后完整性校验（题目数、图片缺失数、答案缺失数）
- **落地动作**：若接入本地 `kaogongzhentizhengliu`，按此流程分步实现，并将完整性校验结果作为数据质量报告产出
- **改动位置**：新增导入脚本（离线一次性运行）
- **预估成本**：1 天（含校验）

### 9.6 零第三方依赖的交付思路

- **来源**：GongkaoNaoku 设计说明（仅用 Python 标准库 `http.server` + `sqlite3` + `json` + `re`，理由是「pip 装不上是交付最大风险」）
- **落地动作**：盘点 GOSHORE 运行时依赖，区分「运行必需」与「离线预处理用」，把后者移出运行时依赖清单
- **预估成本**：2 小时（盘点 + 拆分）
- **注意**：不必照搬到标准库，GOSHORE 已有 FastAPI 体系，重点是**减少运行时装不上的风险**，而非砍掉框架

## 十、数据方面的问题（重点）

以下问题是接入任何外部题库之前必须明确的，逐条列出「现象 / 证据 / 影响 / 处理方案」。

### 10.1 答案与解析的准确性无法保证

- **现象**：题库解析由程序批量生成 + 人工抽检
- **证据**：kaogong 仓库 README 明确写「解析由程序批量生成 + 人工抽检，可能存在错漏，欢迎提 Issue」
- **影响**：若把外部答案当作评阅/判分的金标准，会把错误答案当成正确答案写入 GOSHORE
- **处理**：接入时分两层——「原始答案」与「已核验答案」分开存储并加字段标记；只有核验过的题允许进入种子库。核验方式见第十一节

### 10.2 题库规模口径不一致

- **现象**：同一批素材在不同仓库中标注的题量差异很大
- **证据**：本地 vault 标注 11,282 题（仅资料分析 3,569 + 判断推理 7,713）；GongkaoNaoku 标注 27,506 题（2016–2026 全国各省全模块）
- **影响**：引用规模数据时若不加口径说明，会得出错误结论（例如误以为某仓库缺题）
- **处理**：任何题量引用都必须附「模块范围 + 年份范围 + 统计日期」三要素。写作时建议统一表述为「截至 2026-10-25，GongkaoNaoku 标注 27,506 题，覆盖全模块；本地 vault 为其中的资料分析 + 判断推理子集 11,282 题」

### 10.3 模块覆盖不全

- **现象**：本地 vault 只含资料分析（3,569）与判断推理（7,713）两个模块
- **证据**：vault README「当前收录 资料分析 与 判断推理 两个模块」
- **影响**：GOSHORE 若只接入该 vault，言语理解、数量关系、常识判断三个模块仍无题可用；而行测提分恰恰依赖言语与判断的全覆盖
- **处理**：优先接全模块来源（GongkaoNaoku 的 db 分片），vault 仅作高质量标注补充

### 10.4 重复题与跨卷改编题

- **现象**：同一道题在国考、联考、各省考中反复出现，且常被小幅改编
- **证据**：GongkaoNaoku 覆盖「2016–2026 全国各省」，跨卷重复不可避免；vault 亦有「跨卷聚合真题列表」的考点组织方式
- **影响**：不去重会导致同一知识点被重复推送复习，干扰正确率统计；过度去重又会误删同一考点的变式题
- **处理**：采用两级键——「严格重复」用题干 + 选项内容指纹去重；「同源变式」保留但打上 `variant_group` 标签，统计时可按组去重

### 10.5 题号稳定性

- **现象**：题库重导入后自增 id 会重排
- **证据**：GongkaoNaoku 设计说明明确指出该问题并给出 `qid` 方案；**GOSHORE 实测（2026-10-27）**：`documents.id` 为 `lastrowid` 自增（`db.py` 的 `_upsert`），8 张个人数据表以 `doc_id INTEGER` 为键
- **影响**：若 GOSHORE 用自增 id 绑定复习记录，一次重导入会让所有复习进度错位。**但同库原地重扫不会错位**——`_upsert` 用 `ON CONFLICT(path) DO UPDATE`，path 不变则 id 不变
- **处理**：见 9.1 与第十四节；若无官方稳定题号，必须自建内容指纹作为 `qid`，并把「指纹算法版本」一并记录，便于将来重算
- **分级结论**：官方题库（vault 来源）已有 `qid`，改造量小；**自导入题（手机端 `imp-<批次>-<自增id>`）不稳定，必须一并改造**，否则方案对自建题完全失效

### 10.6 图片与配图版权

- **现象**：题库含大量配图
- **证据**：vault 配图 21,829 张、约 207MB，README 明确「图片版权归原题库平台所有」；GongkaoNaoku 采用 WebP 内置以减小体积
- **影响**：图片随仓库分发存在版权风险；WebP 转换只改变体积，不改变权利归属
- **处理**：个人学习与毕设演示可用；若产品对外分发，图片应改为运行时按需获取或使用自有素材。毕设论文中应写明配图来源与用途限于研究

### 10.7 数据缺失未显式记录

- **现象**：部分题目缺材料、缺图、缺答案
- **证据**：gwy-zhenti 仓库设有独立目录「资料缺失/」，说明该问题普遍存在
- **影响**：静默跳过缺失项会让题库统计失真，后续排查困难
- **处理**：导入时输出「缺失清单」（缺图 / 缺答案 / 缺材料 / 缺解析四类计数），并落盘为报告文件

### 10.8 许可与用途边界

- **现象**：不同项目许可差异极大
- **证据**：见第七节表
- **影响**：混用会导致 GOSHORE 的许可状态被污染（尤其引入 GPL 代码）
- **处理**：建立「来源-许可-用途」登记表，任何引入的数据与代码都登记；GPL 来源只允许参考思路

### 10.9 若接入外部题库，GOSHORE 自身会新增的问题

| 新增问题 | 说明 | 处理方向 |
|---|---|---|
| 数据库体积膨胀 | 全量题库可达数百 MB，桌面安装包体积随之上升 | 题库独立库文件 + 按模块懒加载；安装包只带示例库 |
| 首次加载变慢 | 大库建索引与查询耗时上升 | 索引与题体分库（参考 kaogong-shuati 的 `tiku-index.db` 做法） |
| 数据版本升级 | 题库会持续更新，需版本化 | 参考 GongkaoNaoku 的 `migrate_v2.py` / `migrate_v3.py` 做法 |
| 题目质量参差 | 不同来源质量不一 | 引入 `source` 与 `verified` 字段，界面上标注来源 |

## 十一、数据接入前的验证方案（可写进毕设的数据质量章节）

1. **抽样**：按模块分层随机抽取，每模块 50 题，合计不少于 200 题
2. **四项核对**：题干完整性与选项齐全 / 答案正确性（对照原始真题或权威来源）/ 解析与题目对应关系 / 配图可正常显示
3. **记录错误率**：按「题干错误 / 答案错误 / 解析错位 / 缺图」四类统计，得出各模块错误率
4. **设置准入线**：答案错误率低于阈值的模块方可进入种子库；超标模块降级为「仅练习、不计分」
5. **留痕**：输出抽样清单与核对结论，作为论文数据质量章节与系统内「来源可信度」标注的依据

> 说明：本节的抽样结果需如实报告，包括发现的错误；这部分内容既是工程必需，也是毕设「数据构建」贡献的可信证据。

## 十二、问题解决方法（逐条对应第十节）

### 12.1 答案与解析准确性 → 三源校验 + 核验标记

**目标**：把"外部答案"与"可信答案"分开，杜绝错答入库后污染判分。

**表结构调整**

```sql
-- 在题目表中区分原始答案与核验答案
ALTER TABLE questions ADD COLUMN answer_raw       TEXT;      -- 来源原始答案
ALTER TABLE questions ADD COLUMN answer_verified  TEXT;      -- 核验后答案（可能为空）
ALTER TABLE questions ADD COLUMN verified         INTEGER DEFAULT 0;  -- 0未核验 1已核验 2存在争议
ALTER TABLE questions ADD COLUMN confidence       REAL    DEFAULT 0;  -- 0~1
ALTER TABLE questions ADD COLUMN source           TEXT;      -- 来源仓库/文件
ALTER TABLE questions ADD COLUMN qid              TEXT;      -- 稳定题号，见 12.5

-- 冲突台账：同一题不同来源答案不一致时记录
CREATE TABLE answer_conflicts (
  id INTEGER PRIMARY KEY,
  qid TEXT NOT NULL,
  source TEXT NOT NULL,
  answer TEXT NOT NULL,
  resolved INTEGER DEFAULT 0,          -- 0未解决 1已人工裁定
  note TEXT,
  created_at TEXT DEFAULT (datetime('now','localtime'))
);
```

**三道校验（按成本从低到高，逐级过滤）**

1. **规则校验（程序，毫秒级）**
   - 单选题：答案必须∈选项集合，且仅一个字符（A/B/C/D）
   - 多选题：答案字符数≤选项数，无重复字符
   - 判断题：答案∈{对, 错, 正确, 错误, A, B}
   - 数量/资料题：答案为数值且落在合理区间（如百分比 0~100、增长量可为负）
   - 解析校验：解析文本中必须出现答案对应的选项或数值，否则判为"解析与答案不同步"
2. **交叉校验（程序，秒级）**
   - 若同一 `qid` 在两个以上来源都有答案：全部一致 → `verified=1, confidence=1.0`
   - 出现分叉 → `verified=2`，写入 `answer_conflicts`，`confidence=0`
   - 仅单一来源 → `verified=0, confidence=0.5`
3. **抽样复核（人工或模型辅助，按 11 节方案）**
   - 只对 `verified=0` 与 `verified=2` 的题做抽样，抽样量按模块 50 题
   - 复核结论回写 `verified` 与 `verified_by`

**运行时策略**

| verified 值 | 判分 | 界面表现 |
|---|---|---|
| 1 | 正常判分 | 无标记 |
| 0 | 正常判分但单独统计 | 角标「未核验」 |
| 2 | **不判分**，仅展示解析与争议答案 | 角标「答案有争议」，并在统计中剔除 |

### 12.2 规模口径不一致 → 数据字典 + 统计脚本固化口径

1. 建 `docs/数据字典.md`，固定字段：模块范围、年份范围、来源仓库、统计日期、去重前后题数
2. 写 `scripts/stats_report.py`，每次导入后自动输出 `import_report.json`：
   ```json
   {"generated_at":"2026-10-27","sources":["GongkaoNaoku@master"],
    "by_module":{"资料分析":{"raw":3569,"dedup":3311,"missing_answer":12},
                 "判断推理":{"raw":7713,"dedup":7402,"missing_answer":31}},
    "total":{"raw":11282,"dedup":10713}}
   ```
3. 所有对外表述统一引用 `import_report.json`，禁止口头估算。写作模板：
   > 截至 2026-10-27，题库共 10,713 题（去重后），覆盖资料分析、判断推理；数据来源 GongkaoNaoku master 分支，原始 11,282 题，去重率 5.0%。

### 12.3 模块覆盖不全 → 主库 + 补充库分层

- **主库**：接全模块来源（覆盖言语、数量、常识、资料、判断五模块）
- **补充库**：本地 vault 仅作「深度标注与考点链接」的增强层，以 `qid` 关联，不重复存题
- **界面**：某模块无数据时显示「该模块题库未接入」的空态说明，**不得显示空列表让人误以为已接入**
- **统计**：驾驶舱正确率按模块分列，缺模块不参与总正确率计算（避免分母虚高或虚低）

### 12.4 重复题 → 两级指纹去重

**第一步：归一化（去噪）**

```
去除首尾空白与全部连续空白
全角转半角、统一引号与括号
去除题号前缀（如「1.」「第1题」）
去除「（单选题）」「（多选）」等题型标注
```

**第二步：精确去重（O(1) 查表）**

```python
key = sha256(normalize(stem) + "|" + "|".join(sorted(normalize(o) for o in options)))
```

`key` 相同即严格重复，保留来源最完整的一条，其余记入 `dup_of`。

**第三步：近重复识别（MinHash + Jaccard）**

- 对归一化题干做 3-gram 集合，MinHash 签名（k=128）
- Jaccard ≥ 0.9 判为近重复；0.8~0.9 进入人工复核队列
- 近重复不删除，打 `variant_group` 标签，同组只推送一道复习

**第四步：变式题**

- 题干相似但数值/主体不同的，保留全部，标 `variant_of`
- 统计正确率时可按组聚合（组内任一题答对即视为该考点掌握）

### 12.5 题号稳定性 → qid 生成与迁移五步

**qid 优先级**

1. 题库自带的稳定编号（若有，如「2023国考-地市-判断-045」）
2. 无自带编号时用内容指纹：`sha256(normalize(stem) + "|" + normalize(options))`，取前 16 位
3. 额外记录 `fingerprint_version`（如 `v1`），归一化规则变更时可批量重算并建映射

**迁移五步（已有历史数据时）**

1. 冻结当前题库快照，导出 `(id, 题干, 选项)` 到临时表
2. 为每条记录计算 `qid`，写入题目表并建唯一索引 `UNIQUE(qid)`
3. 建映射表 `id_map(id_old INTEGER, qid TEXT)`，作为一次性过渡
4. 复习/错题/笔记/收藏表中新增 `qid` 列，用映射回填
5. 校验：`SELECT COUNT(*) FROM srs WHERE qid IS NULL OR qid NOT IN (SELECT qid FROM questions)` 必须为 0，方可切换外键并删除旧列

**验收**：重导同一题库两次，`srs` 表中 `due`、`interval`、`lapses` 三个字段零变化。

> **GOSHORE 落地版见第十四节 14.6**：实际表名为 `review_plan` / `wrong_reasons` / `mastery` / `marks` / `doc_notes` / `doc_overrides` / `explain_cache` / `answers`，共 8 张，且 `documents` 在 split 模式下是视图，迁移代码必须写 `content_writer()` 连接。

### 12.6 图片版权与体积 → 内容寻址 + 按需获取 + 打包排除

1. **不入主库**：图片存独立目录 `assets/images/`，题库表只存相对路径或哈希
2. **内容寻址（CAS）**：以文件 sha256 前 16 位命名，天然去重（同一图多题引用只存一份）
3. **清单文件**：`assets/manifest.json` 记录 `qid → image_hash`，便于校验完整性
4. **按需获取**：默认只随包分发前 N 张（如每个模块 200 题内的图），其余运行时下载或提示缺失
5. **打包排除**：PyInstaller 打包配置中排除 `assets/images`，安装包只带示例图
6. **声明**：`NOTICE.md` 写明配图版权归原题库平台，用途限于个人学习与教学研究

### 12.7 缺失静默 → 显式清单 + 界面角标

**导入时输出四类计数**（写入 `import_report.json`）

| 类型 | 判定条件 | 处理 |
|---|---|---|
| 缺图 | 题干/解析含图片引用但文件不存在 | 角标「缺图」，题干仍可练 |
| 缺答案 | `answer_raw` 为空或无法解析 | 角标「缺答案」，**不判分** |
| 缺材料 | 资料分析题无对应材料块 | 整题排除，不进入练习池 |
| 缺解析 | 解析字段为空 | 角标「无解析」，可练不可讲 |

**原则**：缺失项一律显式记录并在界面标注，**不允许静默剔除**——静默剔除会让统计口径失真且无法回溯。

### 12.8 许可污染 → 三级登记 + 隔离

建 `docs/来源与许可登记.md`，三张表分别登记：

| 表 | 字段 | 示例 |
|---|---|---|
| 代码 | 仓库、文件、许可、引入方式（参考/复用）、日期 | xingce-review-pro / writeback.py / GPL-3.0 / **仅参考未复用** |
| 数据 | 仓库、数据类型、许可、用途、是否随包分发 | kaogong vault / 题库 / CC BY-NC / 本地自用，不分发 |
| 文本 | 来源、许可、引用位置 | 方法库文本 / GPL-3.0 / 未复制，独立重写 |

**隔离措施**

1. GPL 来源单独建 `reference_only/` 目录存放"阅读笔记"，**不存放其源码**
2. CI 增加检查：仓库内出现 GPL 头注释即报警
3. 引入 Apache-2.0 代码时，同步更新 `NOTICE` 并注明修改
4. 每次引入前在登记表新增一行，未登记不得提交

### 12.9 接入后新增问题 → 分库、懒加载、版本化、来源标注

| 问题 | 解决方法 | 关键实现 |
|---|---|---|
| 体积膨胀 | 题库独立库文件，安装包只带示例库 | `data/tiku.db` 与 `data/samples.db` 分离，启动时检测 |
| 首屏变慢 | 索引与题体分库 | `tiku_index.db` 只存 qid、模块、考点、题号，查询先走索引库 |
| 加载卡顿 | 按模块懒加载 | 首次进入某模块时才 attach 对应分片 |
| 版本升级 | 版本化迁移 | `PRAGMA user_version` + `migrate_v2.py` / `migrate_v3.py` 顺序执行 |
| 质量参差 | 来源与核验状态可见 | 练习页底部固定显示「来源 / 核验状态」 |

**索引库结构建议**

```sql
CREATE TABLE idx (
  qid TEXT PRIMARY KEY,
  module TEXT, chapter TEXT, point TEXT,
  year INTEGER, region TEXT, exam_type TEXT,
  has_image INTEGER, verified INTEGER
);
CREATE INDEX idx_module_point ON idx(module, point);
```

## 十三、实施顺序与验收标准

### 14.4 三个关键事实（决定改法与优先级）

**事实一：`documents.id` 为自增，同库原地重扫是安全的**

`_upsert`（`db.py` L1284-L1306）用 `ON CONFLICT(path) DO UPDATE`，已存在文件只更新字段、不换 id。所以「重扫同一目录」不会错位——**真正的故障场景只有三个**：换题库源目录、`content.db` 重建、跨设备导入。这决定了 P0 不是「紧急救火」，而是「扩充题库前必须完成」。

**事实二：`qid` 现成可用，且已有双向转换函数**

- `documents.qid` 字段存在（L34），`idx_docs_qid` 已建索引（L51，非唯一）
- `doc_id_by_qid()`（L1542-L1552）、`doc_ids_by_qids()`（L1554 起）已实现 `qid ↔ id` 双向转换
- 实测 vault 11,282 题 `qid` 100% 填充、零重复 → 迁移时不存在「无号可用」的题

结论：**不需要新建 qid 字段体系，只需要把已有 `qid` 提升为主键语义。**

**事实三：自导入题的 `qid` 由自增 id 派生，不稳定（原方案的最大漏洞）**

`mobile_commit_items`（`db.py` L3666-L3685）：

```python
next_id = max(int(row["m"]), MOBILE_MYDOC_ID_BASE   # L3661 常量 10_000_000
qid     = f"imp-{batch}-{new_id}"                    # L3682 ← 批次号 + 自增 id
```

- 同一道题二次导入 → 新批次号 + 新 id → **新 qid**，复习进度无法继承
- `MOBILE_MYDOC_ID_BASE = 10_000_000`（L3661）是为了在 split 模式下让 `documents` 视图的 `UNION ALL` 不与共享库 id 冲突——**这个基数偏移 hack 在 qid 成为主键后可以删掉**
- 因此 P0 必须同时改造：`qid = "imp-" + sha256(normalize(stem) + "|" + normalize(options))[:12]`

### 14.6 v14 迁移（可直接执行）

**前置约束**

- split 模式下 `documents` 是 `TEMP VIEW`，**写它会报 `cannot modify documents because it is a view`**（`db.py` L1321-L1324 已注释说明）→ 所有写操作必须走 `content_writer()`
- SQLite 无 `sha256` 内置函数 → 指纹在 Python 侧算，SQL 只做回填
- 迁移必须幂等：每步先查 `PRAGMA table_info(...)` 再 `ALTER`

**步骤**

```text
Step 0  一致性预检：找 qid 为空 / qid 重复的 documents 行，输出清单，不通过则中止
Step 1  为 qid 为空的行生成指纹（Python 侧）：qid = 'fp-' + sha256(normalize(stem)+"|"+normalize(options))[:16]
        并把自导入题 imp-<batch>-<id> 就地改为同一指纹规则
Step 2  建映射临时表 id_map(id_old INTEGER PRIMARY KEY, qid TEXT UNIQUE)
        INSERT INTO id_map SELECT id, qid FROM documents
Step 3  9 张表 ADD COLUMN qid TEXT，用 id_map 回填
Step 4  建索引：idx_docs_qid 升级为 UNIQUE（WHERE qid<>''）；8 张个人表建 idx_<表>_qid
Step 5  双写开关：写入路径统一先取 qid，写 qid + doc_id；读取路径 qid 优先
Step 6  验收（见 14.7）通过后，才允许把 PK 从 doc_id 切到 qid 并删除旧索引重建
```

**Step 3 回填 SQL（个人库，逐表执行）**

```sql
ALTER TABLE review_plan ADD COLUMN qid TEXT;
UPDATE review_plan
   SET qid = (SELECT m.qid FROM id_map m WHERE m.id_old = review_plan.doc_id);
```

其余 7 张表把表名与键字段替换即可（`wrong_reasons` / `mastery` / `marks` / `doc_overrides` / `doc_notes` 用 `doc_id`；`answers` 用 `doc_id`；`explain_cache` 用 `doc_id`）。

**JSON 两处单独处理**

```text
paper_drafts：读出 ids_json → 逐个 id 查 id_map → 写回 qid 数组
              任一 id 查不到 → 该草稿标记 invalid，不静默删
shared_sets ：同上，但保留原 ids_json 不覆盖，新写入 ids_qid_json 列
```

### 15.3 三个必须如实记录的数据问题

**① 8,001 条作答指向「考点」行 —— 损伤已经发生过**

这些行的 `doc_id` 落在 `kind='考点'` 的文档上（考点没有题干，算不出内容指纹）。成因几乎可以确定：**历史上题库被重建过一次，`documents.id` 整片重排，旧的作答记录就指到了现在这些考点行上**。这正是 14.3 那张表预言的风险，只是它已经在本项目真实数据里发生了。

处理：**不回填、不伪造 qid**。对账把「qid 为空」与「qid 真失联」分成两个口径——前者是历史脏数据（修不了，也不该假装修好），后者才必须为 0。若给考点也编一个 qid，这 8,001 条会突然「解析成功」，看起来健康了，实际是把损伤洗白了。

**② 2 组重复 qid —— 旧规则识别不出、内容指纹能识别**

两组都是 2026-09-26 两次自导入的同一道数量关系题（`imp-20260926160150-001` 与 `imp-20260926161921-001`、`imp-20260926163534-001` 与 `imp-20260926163538-001`）。旧 `imp-<批次>-<自增id>` 规则下它们是两道不同的题，内容指纹把它们认成同一道——这恰好证明改造有效。

处理：**不自动合并**（合并会删用户数据），报告里标出，由人决定留哪条。唯一索引因此降级为普通索引，`_meta.qid_index_mode='plain'` 可查。

**③ 10,381 条空 qid 是「非题目行」，不是漏迁**

`考点` / `材料` 没有 `stem`，`content_fingerprint()` 返回空串（见 `app/qid.py` 的「无题干返回空串」约定）。让它们留空是正确行为：它们不是可练习的题目，`review_plan` / `mastery` / `marks` 这些表的失联数都是 **0**。

### 15.5 一条工程教训

`_migrate_v14` 第一版**在 split 模式下静默回填 0 行**：迁移跑在 `_create_shared_views()` **之前**，那时本连接上还没有 `documents` 临时视图，`SELECT id,qid FROM documents` 直接抛 `no such table`，被 `except sqlite3.Error` 吞掉 → `qid_map` 为空 → 8 张表一行都没回填，而迁移「成功」写入了 v14。

修法：迁移开头先判断 `documents` 是否可读，不可读就补建临时视图。教训是**「容错」和「静默」只隔一层**——迁移里的 `except` 必须至少留下一条能看见的日志，否则失败会伪装成成功。`tests/test_qid_migration.py::test_v14_in_split_mode_backfills_both_files` 守住这条。

### 16.2 三个刻意的设计取舍

**① 只扫代码目录，不扫 `docs/`。** 登记表和调研报告本来就要反复写「GPL-3.0」，把文档纳入扫描只会产生一堆必须加白名单的假阳性——而**假阳性是告警机制的头号杀手**，一旦人习惯性忽略它，真阳性也拦不住了。

**② 不用裸 `GPL` 作标记。** 用「许可证全称」「`SPDX-License-Identifier: GPL*`」「`GPL-3.0` / `GPLv3`」这几种不可能出现在自有代码里的写法，避免命中变量名或讨论性注释。

**③ 不给 `tests/` 开白名单。** 测试要构造 GPL 头来验证拦截能力，做法是把标记**拼接**出来（`"GPL" + "-3.0"`）而不是给目录开口子——白名单就是漏洞。这条规则反过来还验证了守卫真的在扫 `tests/`。

### 16.3 当前结论

全仓代码目录**没有任何第三方源码**。`xingce-review-pro`（GPL-3.0）与 `GongkaoNaoku`（Apache-2.0）都只借鉴思路、独立实现，登记表里逐条写明了「仅参考未复用」。
