# 2026-10-21 AI 质量评测（golden set + scripts/eval_ai.py）

> 配套代码：`app/ai_eval.py`、`scripts/eval_ai.py`、`tests/golden/ai_golden.jsonl`
> 配套测试：`tests/test_eval_ai.py`（15 条）
> 配套基线：33 条 golden、离线 100.00 分、门槛 95 分

## 一、为什么单独做评测

AI 的五条链路（错因归因、时政出题、苏格拉底引导、主观题评分、折纸盒识图）都依赖模型返回**结构化文本**，再由 `app/ai.py` / `app/essay_rubric.py` / `app/cube_vision.py` 的正则和 JSON 容错去解析。这层解析器最怕两件事：

1. **模型输出漂移**：多一层 ``` 围栏、多一句“好的，以下是 JSON”、少一个字段、把 `answer` 写成 `答案：B`，解析器就从“能用”变成“静默丢结果”。
2. **改 prompt 没有量化反馈**：调一句提示词，只能靠手工点几下试，改坏了也看不出来。

单元测试能覆盖“给定这条字符串必须解析成这个结果”，但覆盖不到“真实模型常见的坏输出长什么样”。所以这里做的是**离线的模型输出回归集**：把线上/手工遇到的真实返回录下来，连同“应该被怎么处理”一起固化，每次改 prompt、解析器、评分规则都跑一遍，用分数判断有没有退步。

## 二、组成与数据流

```
tests/golden/ai_golden.jsonl          33 条人工核对的模型原始输出
        │
        ▼
app/ai_eval.py  evaluate_case()       直接调用生产 parser
        │                             错因 / 时政 / 引导 / 作文 / 折纸盒
        ▼
逐条契约检查 → 每条 0~1 分 → 按功能汇总
        │
        ▼
scripts/eval_ai.py                    人类可读报告 / --json / --min-score 门槛
        │
        └── --live：用 input 现场重调模型，--record 写回新 golden
```

评测**不复制**生产解析逻辑，而是直接 import 生产函数。解析器一改，评测立刻反映出来；反过来，评测红了就说明生产链路真的会受影响。

## 三、golden 格式

一行一个 JSON 对象（空行和 `//` 开头的注释行会被跳过）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 全局唯一，重复直接报错（防止复制粘贴改一半） |
| `feature` | 是 | `wrong_reason` / `shizheng_quiz` / `guide` / `essay_grade` / `cube_vision` |
| `raw` | 是 | 模型原始输出，**原样保留**，不改写、不补全 |
| `note` | 否 | 这条在测什么，例如“```json 围栏 + 前后废话” |
| `input` | 否 | `--live` 重录时用的入参（题干/选项/阶段等） |
| `expect` | 否 | 期望结果，如 `{"ok": false}` 表示 parser 应当拒收 |
| `bad` | 否 | `true` 表示这是**故意坏输出**，用于验证校验器能抓住它 |

`bad: true` 的语义要特别说明：它不是说“这条必须解析失败”，而是“这条**不能被当成合格结果放过去**”。有些坏输出仍然能被 parser 解析（比如 JSON 合法但四维不全），这时评测要求契约检查至少报出一个问题；如果一条问题都没报，说明校验太松，直接判 0 分。

## 四、评分口径

每条用例先算 `rate`（通过的检查项 / 总检查项），再折算成该条得分：

| 情况 | 得分 |
|---|---|
| 普通用例，全部检查通过 | 1.0 |
| 普通用例，部分检查失败 | `rate`（保留小数，报告里能看到差在哪） |
| `bad` 用例，被检出问题（`rate < 1`） | 1.0 |
| `bad` 用例，一路放行（`rate == 1`） | 0.0 |
| `expect.ok == false` 且 parser 真的拒收 | 1.0 |

总分 = 所有用例得分的平均值 × 100。基准集当前 **33/33 = 100.00**。

五个功能各自检查什么：

- **错因归因**：可解析；`category` 必须是五类之一（知识盲区/审题失误/计算错误/时间不够/蒙猜）；`specific` / `kaodian` / `advice` 非空；标签与内容不矛盾。
- **时政出题**：题目数量正确；每题恰好 4 个非空选项；答案只能是 A-D；题干不得出现“上述材料/文中/该材料”这类依赖上下文的指代；答案序列与期望一致。
- **苏格拉底引导**：`@@PHASE:probe|hint|answer@@` 被正确剥离；阶段合法；正文不能退化成兜底文案；最后一轮必须强制 `answer`。
- **主观题评分**：总分落在 `0..total`；得分点 5~10 个；状态只能是 命中/部分命中/缺失；四维齐全、顺序与题型预设一致；每维得分不越界；四维之和与总分误差 ≤ 1；`rewrite.revised` 非空；标注分/档/状态序列与期望一致。
- **折纸盒识图**：`is_net` 正确；恰好 6 个格子；6 格四连通；`bbox` 四个数都在 0~1 且不颠倒；非法输出必须抛 `ValueError`，不能“猜一个”返回。

## 五、怎么跑

```bash
# 离线评测（不联网、不花 token）
python scripts/eval_ai.py

# 机器可读 + 卡门槛（CI 用；低于 95 分退出码 1）
python scripts/eval_ai.py --json --min-score 95

# 指定别的 golden 集
python scripts/eval_ai.py --golden path/to/cases.jsonl

# 现场重调模型（需要 API Key；折纸盒用例会明确跳过并报错）
# 必须写到新文件，确认 diff 后再替换基准；--live 单独使用会被拒绝
python scripts/eval_ai.py --live --record tests/golden/ai_golden.new.jsonl
```

`--record` 只写 `--live` 实际拿到的输出，且先写临时文件再原子替换；离线模式不会覆盖 golden。重录后**必须人工看 diff**——模型这次返回得好，不代表旧的那条坏样本可以丢，坏样本恰恰是回归价值最高的。

### 加一条用例的流程

1. 从线上失败、用户反馈或日志里拿一条**原始输出**（脱敏后）。
2. 在 JSONL 末尾加一行，填 `id` / `feature` / `raw` / `note`；如果它本来就该被拒收，加 `"expect": {"ok": false}` 或 `"bad": true`。
3. 先跑评测，确认**新用例是红的**（否则它没有测到任何东西）。
4. 修 parser / prompt / 校验规则，再跑到绿；同时确认总分没有把别的用例拉红。

## 六、和单元测试的分工

- `tests/test_eval_ai.py` 守的是**评测器本身**：golden 必须覆盖五个功能、必须含变异用例、基准必须满分、改坏标签/删四维/超总分必须被抓住、重复 id 与坏行必须报错、CLI 的 JSON/门槛/缺文件退出码正确。
- `tests/test_ai.py` / `tests/test_essay_rubric.py` 等守的是**解析器的具体分支**。
- 两者不重复：前者防止“评测标准悄悄变松”，后者防止“某条正则改坏”。

## 七、局限

- 这是**契约评测**，不是语义 judge：它只能判断“结构对不对、标注的期望有没有被满足”，判断不了“这条错因分析是否真的说到了点子上”。语义质量仍要靠人工抽检（P4 的抽检单）和用户反馈。
- `bad` 用例的“该不该拒收”是人工标注，标注本身可能错；发现误判就改用例，不要为了让分数好看去放宽校验。
- `--live` 有模型随机性，同一条可能这次对下次错；它用于发现新漂移，不适合当 CI 门槛。CI 只跑离线。
- 折纸盒目前没有 `--live`（需要图片输入），只能录真实返回后离线回归。
- 当前 33 条是**首批手工构造的典型输出**（按真实返回的常见形态写），不是从线上日志自动灌进来的；后续应通过 `--live --record` 和用户失败样本逐步替换成真实记录，替换时保留坏样本。

## 八、本机 Windows 跑测试的注意点

Python 3.13 在 Windows 上创建临时目录时会把 `mode=0o700` 落成一条很紧的 DACL；在受限沙箱里，后续 `scandir` 会直接 `WinError 5`。`tests/conftest.py` 顶部对 Windows 做了兼容：创建目录时忽略 mode（Windows 本来也不支持 POSIX mode）。这是测试基础设施补丁，不影响 Linux CI，也不影响运行时行为。

另外仓库根可能残留历史临时目录；`pytest.ini` 已用 `testpaths = tests` 把默认收集范围收进 `tests/`，避免从仓库根递归时扫到无关目录。
