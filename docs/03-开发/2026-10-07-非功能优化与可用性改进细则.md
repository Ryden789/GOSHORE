# GOSHORE 项目 · 非功能优化与可用性改进细则

> **文档性质**：面向执行的 UI / UX、易用性、运行体验与可维护性优化任务书  
> **版本**：V1.0  
> **生成日期**：2026-10-07  
> **读者**：执行开发的模型 / 工程师  
> **目标**：在不增加、删除或改变产品功能及业务规则的前提下，降低上手成本、查找成本和操作不确定性，提升跨设备可读性及运行可预测性。  
> **基线参考**：`README.md`、`交接文档.md`、`docs/README.md` 与当前代码；文档内的行号仅为初始定位提示，执行前必须重新检索确认。

## 1. 执行总则

### 1.1 本轮允许做的事

- 调整信息层级、导航呈现、页面排版、文字说明、视觉反馈和交互反馈。
- 使用当前已有数据与 API 改善状态展示，不增加新的业务数据、服务端接口或数据库字段。
- 改善首次启动提示、错误提示、加载状态、空状态、成功反馈和恢复路径。
- 改善响应式排版、键盘操作、屏幕阅读器标签、对比度、触控目标与减少动态效果支持。
- 优化开发者体验和运行稳定性，但必须保持原有学习、题库、AI、同步、备份等能力和规则不变。
- 增加必要的 UI 静态校验、现有测试断言或手工验收步骤。

### 1.2 本轮禁止做的事

- 不新增产品功能、学习机制、数据维度、导航入口所代表的新能力或新的商业/账号流程。
- 不删除、合并或改变已有功能的业务语义；不改变每日开门题、复习排期、判分、组卷、掌握度、提醒、同步冲突处理等规则。
- 不变更 API 请求/响应契约、数据库 Schema、题库内容、AI 提示词和模型行为。
- 不因“简化界面”隐藏已有功能或让已有页面无法通过原有路径到达。
- 不做大规模前端框架迁移、构建链引入、目录重组或跨端共享架构重写。
- 不顺手清理与本任务无关的代码，不覆盖用户已有改动，不提交、不推送、不发布。

若某项体验改进必须改变业务行为才能完成，应将该项标记为“超出本轮范围”，给出说明，不擅自实现。

### 1.3 执行方法

1. 开始前检查工作区状态，读取本文件、`docs/README.md` 和相关页面当前实现；不得假定行号或旧评审内容仍准确。
2. 用现有页面与路由确认问题，不从旧规划文档直接推断当前缺陷。`docs/03-开发/2026-10-06-修改建议.md` 已有完成状态表，避免重复实施已完成项。
3. 一次只实施一个编号任务，先记录当前表现和复现步骤，再作小范围改动。
4. 桌面端和移动端分别检查。功能或样式相似不代表两端实现相同；涉及两端时均需修改和验收。
5. 每个任务结束时记录修改文件、人工验收结果、自动化检查结果和未覆盖场景。
6. 如果无法实机验证，明确标注“未在真机验证”，不得声称已通过真机验收。

## 2. 项目现状与评估基线

### 2.1 项目事实

- 桌面端入口：`static/index.html`、`static/app.js`、`static/styles.css`。
- 移动端入口：`static/m/index.html`、`static/m/m.js`、`static/m/m.css`。
- 桌面端采用分组侧边导航；移动端采用底部四标签和功能页。两个端是独立实现。
- 项目已有夜间模式、字号档位、行高偏好、页面加载骨架、部分失败重试、空状态、断点续做和局域网访问能力。
- README 说明题库文件不随仓库分发，使用者需自备题源并导入；AI 能力需配置 API Key。
- `start.bat` 当前会尝试结束占用 8765 端口的进程；`run.py` 当前以 `0.0.0.0` 监听服务，并尝试显示局域网地址。这两项需要纳入运行体验与安全边界核对。
- 项目文档记录的质量基线为 pytest 748 条、10 个前端静态校验器和移动端 E2E 72 项断言。执行者应先运行或核对当前分支实际基线，不得把历史数字直接当作本次通过结果。

## 4. 逐项实施细则

### UX-01：首页与导航信息层级

**优先级**：P0  
**参考位置**：`static/index.html` 中 `#nav` 导航；`static/m/index.html` 中 `#tabbar`；桌面、移动首页渲染函数分别位于 `static/app.js`、`static/m/m.js`。  
**问题假设**：功能入口数量较多。用户从首页进入时，需要识别功能分类并记住入口位置；移动端功能页承担大量低频与高频入口。

**目标**：让已经存在的高频学习动作更容易被发现，同时不隐藏或删除任何已有路由和功能。

**实施步骤**：

1. 盘点所有现有导航链接和移动端功能页入口，形成“显示名称 → route → 所属分组 → 当前可见状态”清单；核对每个 route 均仍可到达。
2. 依据现有首页内容突出已有的“继续上次练习”“开始刷题”“今日复习”等常用动作。优先复用当前页面已有数据与跳转，不新增后端请求。
3. 将移动端“功能”页按现有类别分组，分组名应直接表达用途；控制首屏同时出现的入口数量，但不得删除入口或改变路由。
4. 桌面侧栏维持当前分类结构，检查折叠状态下当前页面所在分组仍可识别；活动项、悬停、键盘焦点状态应区分清楚。
5. 若展示数量或状态，只能使用现有接口已有字段；不得为了徽标或排序新增统计接口、数据库字段或后台计算任务。
6. 维持现有页面 URL/hash 路由兼容；历史链接和首页快捷跳转不得失效。

**验收标准**：

- 桌面和移动端全部既有路由仍有可见入口，功能页路由 E2E 不回退。
- 首页首屏可清楚辨认至少一个继续学习入口和一个开始练习入口（当相应状态存在时）。
- 移动端常用入口不需要先进入设置或管理类别才能找到。
- 320px、375px、768px、1366px 宽度下导航无重叠、裁切、横向溢出；键盘可访问桌面侧栏链接。
- 对比优化前后的页面截图，确认没有通过隐藏入口“解决”密度问题。

**禁止事项**：重命名 route、删除入口、改变 tab 语义、自动开始练习、改变首页数据定义。

### UX-02. 首次使用与配置状态说明

**优先级**：P0  
**参考位置**：`README.md` 快速开始、题库规模和 AI 配置章节；`static/app.js`、`static/m/m.js` 首页、题库和设置渲染；后端现有状态 API。  
**问题假设**：首次使用者可能在打开应用后才发现本地题库需要自备，或 AI 需要配置 Key。README 有说明，但页面内缺少集中的状态和下一步信息。

**目标**：在已有功能未就绪时解释其状态和现有解决方式。不得新增注册、引导问卷或配置服务。

**实施步骤**：

1. 检查现有接口和初始化状态，确认页面可读取哪些数据：题库是否为空、AI 是否已配置、当前使用模式、备份/同步是否配置。先复用现有数据，不新增 API。
2. 在首次使用相关页面使用非阻断的状态说明或说明面板；用户关闭后应按当前偏好存储规则处理，不新增用户数据表。
3. 空题库时说明“题库需自行准备并导入”，提供现有导入页链接；不得暗示应用自带完整题库。
4. AI 未配置时，在实际需要 AI 的页面说明需要配置 API Key，并提供直达现有设置入口；纯本地刷题路径不得被 AI 配置阻断。
5. 对手机访问，说明需和电脑处于同一局域网，并显示服务启动时现有的访问地址或解释地址获取方式。
6. 对访客 / 本地模式文案，准确说明数据存储位置和同步状态；不要将“本地存储”误写成“自动云备份”。
7. README 的首次使用部分按“安装依赖 → 启动 → 准备题库 → 可选 AI 配置 → 手机访问”排序，长篇功能清单留在后续章节。

**验收标准**：

- 全新空库状态能让用户知道应用可做什么、题库如何准备、AI 能力如何配置。
- 未配置 AI 不会阻挡已有非 AI 功能；已配置状态不会被错误提示为未配置。
- 每条状态引导都链接到现有页面，路径可用；没有伪造的“一键导入”或自动安装能力。
- 断网、本地模式、空库和正常已配置状态分别检查，文案准确且不重复打扰。
- 运行对应桌面和移动端 E2E / 静态检查。

**禁止事项**：新增强制 onboarding、强制注册、强制配置 AI、改变游客或账号流程。

### UX-03. 每日开门题引导反馈

**优先级**：P0  
**参考位置**：`static/m/m.js` 中 `DAILY_DONE`、`DAILY_LOCKED` 和 `route()` 的守卫；桌面端如有对应行为需一并检索。  
**已知行为**：移动端存在未完成每日开门题时将学习类页面引导回首页的规则。

**目标**：提升规则的可解释性和完成动作的连续性，保留现有规则、拦截范围和每日状态判定。

**实施步骤**：

1. 搜索桌面、移动端所有开门题拦截与提示逻辑，记录触发条件、拦截路由和当前跳转目的地。
2. 将简短 toast 改成清晰、可读且有直接操作的提示：解释当前需要先完成今日开门题，并提供“开始今日一题”入口。
3. 保留原有跳回首页和拦截逻辑，除非项目现有规范明确允许在同页展示提示；不允许直接放行被锁路由。
4. 完成后展示已有的已完成状态，避免用户再次进入时仍收到未完成提示。
5. 说明每日开门题与普通练习的关系，不暗示完成开门题会自动完成学习计划或改变复习安排。

**验收标准**：

- 未完成状态下，原有受限路由依然按原规则受限；完成后放行范围不变。
- 提示在小屏和较大字号下可读，按钮可触摸和键盘聚焦。
- 点击操作只进入现有开门题流程，不产生重复作答或新增记录。
- 对已有每日状态相关测试和移动 E2E 做回归；如当前无覆盖，补充一个针对“路由拦截仍成立”的测试。

**本任务明确禁止**：取消每日开门题、改变受限页面集合、允许跳过、改变每日重置时间或统计口径。

### UX-04. 加载、成功、失败与空状态规范

**优先级**：P1  
**参考位置**：`static/app.js`、`static/m/m.js` 的 `route()`、各页面请求处理和现有 `emptyState()` / toast；`static/styles.css`、`static/m/m.css`。

**目标**：用户能判断系统正在做什么、操作是否成功，以及失败后如何恢复。

**实施步骤**：

1. 梳理页面加载、表单提交、AI 请求、导入、备份、恢复和同步中的提示实现，优先整理重要任务，不要求一次性重写所有旧页面。
2. 统一提示语结构：发生了什么 → 当前结果/影响 → 用户可执行的下一步。避免只显示“失败”或只把异常字符串原样抛给用户。
3. 保留技术细节用于诊断；面向用户的主提示不显示 Python traceback、SQL、内部路径或原始堆栈。
4. 请求开始时立即禁用重复提交，并提供可感知的加载反馈；结束时恢复按钮状态。不得让按钮永久禁用。
5. 对支持安全重试的请求提供显式“重试”；对非幂等提交、恢复、清空等操作不得盲目自动重试。
6. 空数据状态应区分“尚无内容”“筛选无结果”“内容读取失败”“功能未配置”。保留对应页面现有空状态，不用错误提示代替空状态。
7. 成功反馈要说明结果，例如保存成功、导入 N 条、同步完成；只使用真实返回数据，不能展示猜测的数量。
8. 对关键提示使用 `role="status"` / `aria-live` 等适当语义，避免仅靠颜色表达成功或错误。

**验收标准**：

- 对页面加载、提交中、成功、空结果和失败至少各选一个真实流程，在桌面和移动端完成验收。
- 快速重复点击不会产生重复提交；失败后按钮可恢复或页面有明确返回路径。
- toast 不承载长篇说明；重要错误不会在用户阅读前自动消失。
- 屏幕阅读器可感知重要状态变化；禁用按钮样式与禁用原因可辨认。
- 运行现有全量测试和 E2E；不为了统一文案改变错误码或接口行为。

### UX-05. 设置页信息组织

**优先级**：P1  
**参考位置**：桌面端与移动端设置渲染函数（可在 `static/app.js`、`static/m/m.js` 搜索 `renderSettings` 或“设置”定位）。

**目标**：用户能快速找到偏好、AI、提醒、同步、备份和数据管理，并能理解设置是否生效。

**实施步骤**：

1. 先对比桌面和移动设置页已有字段、按钮和说明，列出差异；不得因为版式不同遗漏现有能力。
2. 按现有功能归类为：学习与外观偏好、提醒、AI 配置、备份与同步、数据管理、应用/连接信息。可以使用标题、目录锚点或折叠区，但不改变设置值和保存 API。
3. 视觉上区分普通偏好和破坏性操作；清空/重置确认继续沿用现有保护步骤和影响范围说明。
4. 标明需要点击保存的设置与立即生效的设置；仅以实际实现为准，不改变保存时机。
5. 对同步设置展示当前已有的连接/配置状态和最近一次实际操作反馈；若没有可用的“最近同步”数据，保留原布局并在文档记录缺口，禁止新增字段或接口来补齐。
6. 增加设置页内的标题导航或锚点时，保证移动端可见、可点击且不会被顶部固定栏遮挡。

**验收标准**：

- 设置项与修改前一一对应，桌面和移动端没有功能遗漏。
- 所有保存、测试连接、导出、恢复和清理操作仍调用原有处理逻辑。
- 破坏性操作的确认文本仍准确说明数据范围，原有确认次数与勾选要求不降低。
- 小屏和特大字号下标签、输入框、说明和按钮不重叠；键盘焦点顺序合理。

### UX-06. 小屏、字号、键盘与无障碍检查

**优先级**：P1  
**参考位置**：`static/styles.css`、`static/m/m.css`；前端页面内联 SVG、图表和固定操作栏；现有 `tools/check_svg_fit.mjs`、`tools/check_appearance.mjs`。

**目标**：改善已有页面在狭窄屏幕、大字号、深色模式、键盘和辅助技术下的可读性与操作性，不新增无障碍功能模块。

**实施步骤**：

1. 测试宽度：320、360、375、430、768、1024、1366 CSS px；至少覆盖首页、组卷、答题、错题、辨析卡、速查手册、设置和统计图页面。
2. 覆盖字号最小和最大档、浅色/深色、行高宽松开关、移动端安全区和软键盘打开状态。
3. 检查页面是否出现非预期横向滚动、被固定导航遮挡、按钮文字截断、标签重叠、表格无法访问或公式裁切。

### OPS-01. 启动与局域网连接可预测性

**优先级**：P1  
**参考位置**：`start.bat`、`run.py`、`app/config.py`、README 手机访问说明。

**目标**：减少端口冲突导致的误操作，并让用户更容易判断服务是否启动、手机是否可连接。此项属于运行维护体验，不改变应用业务功能。

**实施步骤**：

1. 审核 `start.bat` 当前释放端口逻辑。默认行为不得静默或强制结束不属于本应用的进程。
2. 对端口占用场景给出明确 PID/占用提示和可恢复路径。优先尝试复用当前服务或提示用户处理；如采用交互确认，确认前不得终止进程。
3. 保持默认端口配置契约不变。只有在现有配置支持的情况下才允许用户选择其他端口；不得引入未文档化的端口变更或让手机入口指向错误端口。
4. 检查局域网 IP 推导逻辑在无互联网、多个网卡、VPN、Wi-Fi 断开时的结果。不能确定地址时明确显示“未能自动检测”，提供不依赖外网的人工查找说明。
5. 明确告诉用户服务正在局域网监听，手机和电脑需要处于同一可互访网络；不声称服务只对本机开放。
6. 核对本地数据、API Key、WebDAV 凭据和日志中不输出明文秘密。
7. 对 `0.0.0.0` 监听范围做风险说明和最小化检查；不得在本任务中未经需求确认改成破坏手机访问的仅本机监听。

**验收标准**：

- 8765 未被占用时现有启动方式仍可启动，并显示实际电脑和手机访问地址。
- 端口被其他进程占用时，不会自动结束该进程；用户能看懂如何处理。
- 无互联网但局域网可用时，服务仍能启动；地址推导失败时错误说明准确且不假报 `127.0.0.1` 为手机可访问地址。
- 手机在同一 Wi-Fi 下可按提示访问；不同网段/无法访问时提示不会承诺连接成功。
- 使用模拟占用端口、无外网网卡和普通启动场景做手工检查；记录系统版本和结果。
