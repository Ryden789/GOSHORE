## §A 目标与边界

| 编号 | 目标 | 判定方式 |
|---|---|---|
| G1 | AI 答疑除图片外，支持上传文本类文件（txt/md/csv/json/代码）与 Word（.docx） | 选中文件后出现附件条，发送时内容进入模型上下文 |
| G2 | 申论批改的题目 / 材料 / 作答三框均可「上传文件」导入文字 | 三个框都能各自导入，结果追加而非覆盖 |
| G3 | 申论批改支持上传图片，OCR 出文字后填入指定框 | 拍照/截图 → 识别 → 文本落地，失败有明确中文提示 |
| G4 | 双端同源：桌面（FastAPI）与安卓内置服务（`goshor_server`）行为一致 | 同一份 JSON 契约，两端路由都通 |
| G5 | 体量与安全边界明确：单文件、单请求、总字数都有上限，超限给可读提示 | 超限返回 400 + 中文原因，不吞异常 |
| G6 | 不新增 Android 端不可用的运行时依赖 | Android 侧只用 stdlib + `httpx`，PDF 明确降级 |

**不做**：
- 不做 PDF 在手机端的解析：安卓包里没有 `pymupdf`，装不进（离线 wheels 只有 7 个包）。手机端对 PDF 给「请用电脑导入，或截图后上传图片」的明确指引，不假装支持。
- 不做扫描版 PDF 的 OCR：没有页面渲染能力（`pymupdf` 在桌面才有），拿不到图就没法喂视觉模型。
- 不做附件持久化：文件文本只存在于当次请求/输入框，不落库、不入 localStorage（避免把几万字塞进 5MB 配额）。
- 不改 `/api/ai/ask` 的既有图片契约（3 张、JPG/PNG/WebP、base64）。

## §C 方案与取舍

- **选定（传输格式）**：文件走 JSON + base64 data URL（`{"name","data_url"}`），不用 multipart。理由：安卓端 `goshor_server` 是手写 `BaseHTTPRequestHandler`，解析 multipart 要自己写边界切分，是个纯负担；而 base64 与既有图片上传同一套心智，双端一个解析器就够。
- **选定（docx 解析）**：`app/attach.py` 用 stdlib（`zipfile` + `xml.etree`）解 `word/document.xml`，按 `w:p` 切段、`w:t` 取字。否决 `python-docx`：它是**可选**依赖，安卓端没有，用了就会出现「桌面能传、手机报 ImportError」的双端分裂。
- **选定（PDF）**：桌面用 `fitz`（`pymupdf`）抽文本层，抽不到（扫描件）就明确返回「这是扫描版 PDF，请截图后按图片上传」；安卓端直接返回「请在电脑端导入 PDF」。否决「两端都装 pymupdf」：安卓 wheel 不在离线源里。
- **选定（OCR）**：新写 `app/ocr.py`，单轮非流式，`mode` 区分 `essay`（按手写稿逐字转写、保留分段、不纠错）与 `general`（通用转写）。否决复用 `cube_vision`：那个 prompt 是为六格展开图定制的，返回 JSON，复用它得改 prompt 又会破坏折纸盒功能。
- **选定（前端交互）**：申论三个 textarea 各配一个极简工具条（「📎 文件」「📷 图片」），`data-target` 指到哪个框就填哪个，结果**追加**不覆盖（用户可能已经手打了一段）。AI 答疑只用一个按钮，图片继续走既有预览缩略图，文件则折成一条「📄 文件名 · N 字」的附件条。
- **选定（字数上限）**：单文件解析后 ≤ 20,000 字（超出截断并提示），附加到提问的文本 ≤ 8,000 字（模型上下文与 localStorage 双重考虑）。否决「不设限」：一份 5 万字的材料贴进 `answer` 会让批改提示词爆掉，模型反而抓不住要点。
