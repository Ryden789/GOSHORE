# P1 备份清单与诊断

> 2026-10-26 · P1 数据可靠性<br>
> 目标：让用户知道“备份是否完整、能不能恢复、上次备份是什么时候”，而不是只看到一个 zip 下载按钮。

## 一、问题

旧备份包只有 `goshor.db`、`settings.json`、`essay_questions.json` 三个文件。恢复时只校验 SQLite 能不能打开，无法区分：

- 下载/传输中被截断的包；
- 被其他工具改写过的包；
- 来自更新版本、当前版本不认识的包。

同时设置页没有“当前有多少数据、上次什么时候备份”的反馈，用户只能凭记忆判断。

## 二、备份清单

导出时在 zip 根目录写入 `manifest.json`：

```json
{
  "format": 1,
  "app": "goshore",
  "created_at": "2026-10-26T18:00:00",
  "db_bytes": 229376,
  "db_sha256": "……",
  "split": true
}
```

- `format`：清单格式版本；当前为 `1`。
- `db_bytes` / `db_sha256`：zip 内 `goshor.db` 的字节数与 SHA-256。
- `split`：导出时是否处于双库模式（zip 内文件仍叫 `goshor.db`，内容是个人库）。
- 文件名保持 `goshor.db`，旧版导入端和手机端不需要改。

## 三、导入校验

`POST /api/backup/import` 按以下顺序处理：

1. zip 中必须有 `goshor.db`；
2. 用 SQLite 打开并执行 `SELECT 1`，排除伪文件/损坏库；
3. 有 `manifest.json` 时解析并校验：
   - 清单损坏 → 拒绝；
   - `format > 1` → 提示“来自更新版本，请先升级 GOSHORE”；
   - `db_sha256` 不匹配 → 拒绝，且**不覆盖现有个人库**；
4. 通过校验后才替换个人库；`split` 模式会清掉误写进个人库的题库表；
5. 没有清单的旧包仍可导入，返回 `verified: false`，兼容旧备份。

## 四、备份诊断

`GET /api/backup/status` 是只读接口，返回：

| 字段 | 含义 |
| --- | --- |
| `ok` / `integrity` | 个人库 `PRAGMA quick_check(1)` 是否通过 |
| `split` | 是否双库模式 |
| `content_bytes` / `user_bytes` | 题库库、个人库体积 |
| `answers` / `notes` | 作答数、题目笔记数 |
| `last_backup_at` | 上次成功导出时间（导出成功后写入 settings） |
| `data_dir` | 当前数据目录，便于用户确认便携/ LocalAppData 位置 |

手机端“设置 → 备份与恢复”显示：

> 个人库 0.2 MB · 12 条作答 · 3 条笔记 · 上次导出：2026-10-26 18:00

没有导出过时显示“还没有导出过”。

## 五、测试

`tests/test_backup_manifest.py`：

- 导出包含清单，`db_sha256` 与实际 db 一致；
- 正常导入 `verified: true`；
- 篡改 db 后拒绝覆盖，错误含“校验失败”；
- 旧版无清单 zip 可导入，`verified: false`；
- 新用户状态：`answers=0`、`user_bytes>0`、`last_backup_at` 为空；
- 导出后状态记录 `last_backup_at`。

当前全量基线：**1019 passed**（2026-10-26），16 个静态校验器 EXIT=0。

测试用 `monkeypatch` 把 `main.DATA_DIR`、`main.SETTINGS_PATH`、`config.SETTINGS_PATH` 都指向 `tmp_path`，避免读写真实 `data/`。

## 六、边界

- 清单只防“传输损坏/误改”，不防恶意伪造；备份包仍应存放在自己可控的位置。
- `last_backup_at` 记录的是“成功生成导出文件”，不代表用户已把文件保存到网盘/微信。
- 备份仍只含个人数据，不含 `content.db` 题库；换机后题库由安装包/更新包提供。
- 尚未做真实用户恢复演练；当前以自动化测试覆盖为主。
