## 一、桌面软件版

### 1.1 为什么要单独处理路径

PyInstaller `--onefile` 运行时，会把整个归档解压到一个**每次启动都新建、退出即删除**的临时目录
（`sys._MEIPASS`）。如果用户数据（SQLite 库、设置、WebView 存储）也按 `__file__` 推导，
就会写进这个临时目录 —— **关闭窗口后题库和作答记录全部消失，且不报错**。

`app/config.py` 因此把两类目录分开算：

| 常量 | 源码运行 | 冻结成 exe | 用途 |
|---|---|---|---|
| `BUNDLE_DIR` | 仓库根 | `_MEIPASS` | 只读资源（`static/`、`app/*.json`） |
| `BASE_DIR` | 仓库根 | **exe 所在目录** | 用户数据根 |
| `DATA_DIR` | `<根>/data` | **`<exe目录>/data`** | 库、设置、日志、WebView 存储 |

判断依据是 `getattr(sys, "frozen", False)`。

**已验证**（模拟冻结环境）：

```python
sys.frozen = True
sys._MEIPASS = r"C:\Temp\_MEI12345"
sys.executable = r"D:\GOSHORE-Desktop\GOSHORE上岸工作台.exe"
# → DATA_DIR = D:\GOSHORE-Desktop\data
# → users_dir 不含 _MEI  ✅
```

> 审查中曾有一条"严重"判断称 `db.py` 的 `users_dir = DB_PATH.parent / "users"`
> 会派生出 `_MEIPASS\data\users` 导致账号数据每次重启丢失。**实测证伪**：
> `DB_PATH` 本身已由 `DATA_DIR`（= `BASE_DIR/data`）算出，冻结后正确指向 exe 目录。

### 1.2 打包链路

| 文件 | 职责 |
|---|---|
| `desktop_entry.py` | exe 入口。`--windowed` 下 `sys.stdout/stderr` 为 `None`，先重定向到 `data/logs/desktop-YYYYMMDD.log`，否则任何 `print` 都会抛 `AttributeError` |
| `desktop.py` | 后台线程跑 uvicorn（`webview.start()` 必须占主线程）；WebView2 原生窗口；端口占用时复用已有实例而非杀进程 |
| `tools/build_desktop_exe.py` | PyInstaller 封装：`--onefile --windowed`、图标、版本资源、`--add-data static/` 与两个 `app/*.json`、可选依赖 `--hidden-import` |
| `tools/create_shortcut.py` | 桌面快捷方式（`--public` / `--remove`） |
| `tools/make_desktop_icon.py` | 由 `static/icons/icon-512.png` 生成 6 尺寸 `.ico` |

**刻意不打包 `data/`**：用户学习库动辄数百 MB，打包会撑大体积、让用户数据随版本被覆盖，
也无法把软件单独发给别人。产物约 89.5 MB。

### 1.3 三个关键实现细节

1. **uvicorn 必须传 app 对象，不能传 `"app.main:app"` 字符串**
   字符串要 uvicorn 运行时重新 import，而打包后模块在 PYZ 归档里，会报
   `Could not import module "app.main"`。

2. **首次建大题库会超过固定超时**
   实测导入 23,491 篇 md 耗时 **259 秒**。原实现固定等 30 秒即判"启动失败"。
   现改为：**端口一旦监听**就说明进程活着并在跑 lifespan，把等待上限放宽到 600 秒，
   每 10 秒打印进度；只有进程报错退出才提前返回失败。

3. **`private_mode=False` + 固定 `storage_path`**
   pywebview 默认隐私模式会每次清空 localStorage，导致主题、字号、开门跳过标记全部丢失。

### 1.4 部署位置的经验

测试中发现：exe 放在 `D:\GOSHORE`（项目目录）下**启动几秒即静默退出**，连 `data\` 都不创建；
同一 exe 放到 `%TEMP%`、`D:\gs-b` 均正常。

根因是该项目目录带有一条 ACL：

```
Everyone : DENY  DeleteSubdirectoriesAndFiles
```

exe 向自身目录写 `data\` 时被拒绝，而 `--windowed` 无控制台，表现为"双击没反应"。
最终部署到 `D:\GOSHORE-Desktop\`（干净可写目录）。**若你的目录有类似策略，请换位置。**

## 二、全局缺陷修复（实测确认）

以下每条都**先复现、再修复、再验证**；未经实测的审查结论一律不采纳（见第四节）。

### 2.1 严重

**`/img` 可读取任意文件**（`app/main.py`）

`vault_path` 默认值改为空串后，`Path("")` 等于当前目录且 `Path("").exists()` 恒为 `True`，
越界校验退化成"不许出工作目录"。

```text
复现：GET /img?path=data/secret.txt  →  200 'TOP-SECRET-CONTENT'
```

**影响**：同局域网任意设备可下载 `data/settings.json`（含 DPAPI 密文与其他配置）和 `data/goshor.db`。

**修复**：空 vault 直接 404；加 `is_dir()` 校验；**限定图片后缀白名单**（否则 vault 里的 md/json 也能被读）。

```text
验证：空 vault → 404 ；正常图片 → 200 ；.md → 403 ；../ 穿越 → 403
```

**`accounts.set_session` 并发必定 500**（`app/accounts.py`）

`tmp` 文件名固定为 `session.json.tmp`，Windows 上 `Path.replace` 撞到读句柄抛 `PermissionError`。
而手机端**每个请求**都会先读会话文件。

```text
复现：边读边写 300 次 → 写入失败 291 次，读取失败 14 次
```

**修复**：模块级 `threading.Lock` + tmp 名带 `pid/线程号` + 退避重试，最终失败退化为直接覆盖写。

```text
验证：3 写线程 ×60 次 + 3 读线程 ×200 次 → 0 异常，0.17s，无残留 tmp
```

### 2.2 中等

**`save_settings` 并发丢失 + 非原子写**（`app/config.py`）

读-改-写无锁，`write_text` 非原子。多标签页同时保存会互相覆盖且静默返回 `ok`；
进程中途被杀留下半截 JSON，`load_settings` 解析失败后**静默回落默认值**，用户所有设置"凭空消失"。

修复：`RLock` 包住整个读-改-写 + 临时文件 `os.replace` 原子替换（带 Windows 重试）。

```text
验证：20 线程并发写不同键 → 零丢失，JSON 合法，无残留 tmp
```

**`importer.commit_items` 未拦空 vault**（`app/importer.py`）

同 `Path("")` 根因：清空 vault 后导入会在**进程工作目录**下造出 `99-自导入/`，返回 `ok:true`，
而 `reindex` 永不收录 → 用户看到"导入成功却找不到题"。

修复：抽出 `_vault_or_error()` 统一拦截，空串/不存在都返回明确错误。

**测试自身的 GBK 解码缺陷**（`tests/test_doc_notes.py`、`tests/_search_history.py`）

`subprocess.run(..., text=True)` 在中文 Windows 上默认按 GBK 解码 node 的 UTF-8 输出，
抛 `UnicodeDecodeError` 使 `stdout` 为 `None`，导致断言报 `TypeError`。

修复：显式 `encoding="utf-8", errors="replace"`，并把断言从过时的"全部通过"放宽为"通过"。

> 这条很关键：那 2 个"失败"**不是被测代码的问题**，校验器本身一直全绿（74 条断言通过）。
> 若不查证就"修校验器"，会去改本来正确的代码。

### 2.3 轻微

| 位置 | 问题 | 修复 | 验证 |
|---|---|---|---|
| `static/m/m.js` | 裸引用 `GoshorNative`，桥未注入时整页 `ReferenceError` | 统一 `window.GoshorNative` + 入口判空 | 无残留裸引用 |
| `static/app.js` | 组卷页每次进入泄漏 3 个全局监听 + 游离 `kdDrop` 节点 | 绑到 `abortCtl.signal`，abort 时移除节点 | `.kd-drop` 计数：修复前 1 → 修复后 0 |
| `static/sw.js` | `!k.startsWith(VERSION)` 清理缓存会误删；离线缺 cube 资源 | 精确比对两个缓存名；补 cube 三件套 | 语法校验通过 |
| `desktop.py` | `[✓]` 在 GBK 控制台抛 `UnicodeEncodeError`，窗口不出现 | `sys.stdout.reconfigure(errors="replace")` | 自检 6/6 通过 |
| `start.bat` | 端口写死 8765，用户改端口后仍打开空白页 | 从 `settings.json` 读取实际端口；`findstr` 改精确匹配 | 实测能读到 8799 |

## 四、被证伪的审查结论（重要）

全局审查由 4 个子代理并行完成，报回约 40 条。**以下两条判为"严重"的结论经实测证伪，未采纳**：

1. **"用户数据写入 `_MEIPASS`，关窗即丢"**
   → 模拟冻结环境实测 `users_dir` 正确落在 `exe\data\users`。根因是审查者把
   `DB_PATH.parent` 误当成 `_MEIPASS` 派生。**若照改，反而会引入真实 bug。**

2. **"`importer.fetch_url_text` 的 5MB 上限失效"**
   → 子代理自己复核后撤回（`aiter_bytes()` 的小 chunk 能正常累加 `total`）。

**教训**：审查报告必须逐条复现后才改代码；"看起来对"的重构建议风险最高。
