## 第一档：立即加固（防未来踩坑，成本低）

### 建议 1　`/api/mastery` 默认全量返回，存在拉取 1.45MB 的风险

**位置**：`app/db.py` 约 L1814-L1837，函数 `kaodian_mastery_page()`

**现状**：
```python
lim = int(limit or 0)
page = rows[off:off + lim] if lim > 0 else rows[off:]   # limit=0 / 不传 → 返回全量
```

**问题**：实测不带参数裸调 `/api/mastery` 返回 **1.45MB**。当前前端带了分页参数没有踩坑，但任何新客户端（PWA、分享页、以后的新页面）一旦忘记传 `limit`，手机端一次性渲染上万行会卡死（首屏 4 秒以上）。

**修改步骤**：
1. 把默认行为改为「安全上限」。示例：
   ```python
   DEFAULT_LIMIT = 300

   # 调用方语义：
   #   不传 / limit=0 → 取 DEFAULT_LIMIT 条（安全默认）
   #   limit > 0      → 取指定条数
   #   limit = -1     → 显式要全量
   lim_raw = int(limit)
   if lim_raw < 0:
       page = rows[off:]                 # 显式全量
   else:
       lim = lim_raw or DEFAULT_LIMIT
       page = rows[off:off + lim]
   ```
2. 同步检查 `app/main.py` 里 `api_mastery`（约 L555-L562）的参数透传，确认 `-1` 能传到 db 层。
3. 移动端 `android/app/src/main/python/goshor_server.py` 约 L689 `/api/mastery` 分支使用的是同一 db 函数，无需单独改，但要回归。
4. 前端 `static/m/m.js` 的 `renderMastery`（L2889）和 `static/app.js` 的 `renderMastery`（L5155）已显式传 limit，确认行为不变。

**验收**：
- 不带参数调 `/api/mastery`，返回条数 ≤ 300
- 传 `limit=-1` 能取全量
- 加一条 pytest：断言默认返回 `len(items) <= 300`

**预估工作量**：0.5 天

### 建议 2　AI 接口缺少「未配置 Key」的自动化测试

**位置**：测试目录 `tests/`；涉及降级逻辑在
- `app/main.py` L1355（批改：JSON 失败降级纯文本）
- `app/main.py` L1457（面试：同上）
- 错因 AI 归因（`/api/wrong-reason/ai-suggest`）

**现状**：各 AI 功能都写了「解析失败/无 Key」降级代码，但现有 158 个测试**没有断言未配置 Key 时接口不崩溃、确实走了降级路径**。免费用户（不配 Key）是重要用户群，这个路径以后很容易被改坏而无人发现。

**修改步骤**：
1. 参考 `tests/test_api.py` 已有的 `client` fixture（临时库、预置 1 道题）。
2. 新增用例，思路：
   ```python
   def test_essay_grade_without_key(client, monkeypatch):
       # 让读取设置返回空 Key（monkeypatch 设置读取函数，或直接写空设置）
       monkeypatch.setattr("app.ai.load_settings", lambda: {"deepseek_api_key": ""})
       r = client.post("/api/essay/grade", json={...合法最小参数...})
       # 关键断言：不返回 500，且响应里有降级提示
       assert r.status_code == 200
   ```
3. 对面试 `/api/interview/grade`、错因 AI 各加 1 条同类用例。
4. 若实际代码在无 Key 时返回的是特定错误码（如 400 + 提示），则按实际契约断言，**不要为了凑 200 改业务代码**——先读现有降级实现，测试对齐它的真实行为。

**验收**：新增 2~3 条用例；`pytest tests -q` 全绿；故意清空 Key 时无 500。

**预估工作量**：0.5~1 天

### 建议 3　时政流水线依赖联网，CI 无法回归解析逻辑

**位置**：`scripts/update_shizheng.py`；人民网解析类 `LinkParser`（约 L59 起）

**现状**：流水线必须访问 `politics.people.com.cn`，GitHub Actions / 离线环境下无法测试「链接提取、去噪、期次归档、去重」这些纯解析逻辑，解析出 bug 只能等真联网才暴露。

**修改步骤**：
1. 在 `tests/fixtures/people_1024_sample.html` 放一份**固定的、手工脱敏的**人民网列表页 HTML（自己构造 5~8 条 `<a>` 即可，含 2 条应被 `NOISE` 规则过滤的噪声）。
2. 给 `scripts/update_shizheng.py` 增加入参：
   ```python
   parser.add_argument("--html-file", help="从本地 HTML 读取，不联网（测试用）")
   ```
   抓取函数在传入该参数时直接 `Path(html_file).read_text()`，跳过网络请求。
3. 新增 `tests/test_shizheng_pipeline.py`：
   - 用本地 HTML 跑解析，断言提取出正确条数
   - 断言噪声条目被过滤
   - 断言同一批跑两次不产生重复（去重生效）
4. 注意退出码约定（0 成功 / 2 无网 / 3 无 Key），离线 fixture 路径下应正常返回 0。

**验收**：新用例不联网也能跑过；`pytest tests -q` 全绿；CI 中该用例稳定通过。

**预估工作量**：1 天

## 第二档：近期优化（质量与体验）

### 建议 4　验证自适应推题是「真加权」而非仅跑通

**位置**：`app/db.py` `adaptive_paper()`（约 L1702）

**问题**：目前只能确认接口返回了题目，无法从结果证明「掌握度低的题确实更容易被抽中」。加权 SQL 一旦被误写成普通随机，功能静默失效。

**修改步骤**：
1. 加一条统计型 pytest：
   - 临时库预置一批题，让其中某题连续答错（`add_answer(correct=False)` 多次），拉低其 mastery
   - 重复调用 `adaptive_paper()` 约 500 组，统计该题命中频次
   - 断言其命中频次显著高于均匀基线（例如用宽松阈值：高于基线 1.5 倍）
2. 该用例运行可能稍慢，可把抽样组数控制在 300 左右，或用确定性种子。

**验收**：用例能在加权被改成随机时失败、在正确实现时通过。

**预估工作量**：0.5 天

### 建议 5　小屏下 SVG 图表适配实测

**位置**：
- 能力雷达（`static/m/m.js` 约 L937 `renderPlan`）
- 错因分布圆环（`static/m/m.js` 约 L1910-L1948）

**问题**：六边雷达、圆环图在宽度 <360px 的机型（iPhone SE、小屏安卓）可能溢出或标签重叠，静态代码检查发现不了。

**修改步骤**：
1. 所有内联 SVG 统一用 `viewBox="0 0 …"` + `width="100%"`，不要写死像素宽。
2. 用 Chrome DevTools 设备模拟（iPhone SE 375px、再手动改到 320px）逐页查看：
   - 雷达是否横向溢出、六个角标签是否压字
   - 圆环与图例是否换行正常
3. 文字标签必要时随宽度缩短，或最小字号不低于 10px。

**验收**：320px 宽下无横向滚动条、无文字重叠；有真机可在真机再确认一次。

**预估工作量**：0.5~1 天

### 建议 6　排查偏慢的测试用例

**位置**：`tests/`

**现状**：全套测试 25.9 秒，对一个本地项目偏慢，可能有用例绕过临时库打到了真实 `data/goshor.db`。

**修改步骤**：
1. 运行：
   ```bash
   python -m pytest tests -q --durations=10
   ```
2. 查看最慢的 10 个用例，重点确认：
   - 是否每个用例都通过 fixture 把 `db.DB_PATH` 指到了临时目录
   - 是否有重复 `init_db()` / 全表扫描 / 真实联网等待
3. 对慢用例：复用连接、减少预置数据量、把可共享的初始化提升到 session 级 fixture。

**验收**：确认没有用例读写真实库；总耗时有可见下降（目标 <20 秒）。

**预估工作量**：0.5 天

## 第三档：中期增强（按需）

### 建议 7　新表内容为空时给「建设中」提示

**位置**：面试、时政等新模块页面；可复用现有启动自检 `_startup_selfcheck()` 框架。

**问题**：新表无数据时页面可能呈现空白，用户不知道是坏了还是没内容。

**做法**：
1. 在对应页面判断列表为空时，渲染统一的空状态：「内容建设中，可先用 XX 功能」并给出一个可点的替代入口。
2. 启动自检增加对新模块表的可访问性检查（沿用现有 facets/list_exams 的检查模式）。

**验收**：清空对应表后页面显示明确空状态而非白屏；自检输出包含新项。

**预估工作量**：1 天

### 建议 8　答题卡接入「涂卡练习」

**位置**：`static/m/m.js` 答题卡组件（约 L1532 起）、桌面对应组件

**问题**：资料分析里「只填最终答案」的题目前仍逐题判分，不符合真实考试先做题、最后统一涂卡的习惯。

**做法**：
1. 考场模式下允许只在答题卡录入答案，题目区不强制即时作答。
2. 交卷时按答题卡录入统一判分。

**验收**：可以只通过答题卡完成一整组资料分析并得到正确结算。

**预估工作量**：1.5 天

### 建议 9　掌握度衰减的性能监控

**位置**：`app/db.py` `decay_mastery()`（约 L1658）；调用点在 `/api/stats`（约 L2026）

**问题**：衰减虽有 1 小时节流，但题库继续增长后，首次触发的批量衰减可能拖慢 `/api/stats`。

**做法**：
1. 给衰减过程加耗时日志。
2. 超过 200ms 时改为后台分批执行，不阻塞 stats 返回。

**验收**：题库扩大后 `/api/stats` 响应不被衰减明显拖慢；日志可观测。

**预估工作量**：1 天

## 通用执行规范

所有修改必须遵守：

1. **数据库变更**：新表/新列一律走 `_migrate()` 并把 `SCHEMA_VERSION` +1，禁止散装 ALTER。
2. **双端同步**：接口改动同时确认桌面 `app/main.py` 与移动端 `android/app/src/main/python/goshor_server.py`；移动端只读 ATTACH 库不可写入。
3. **AI 调用**：要求 JSON 输出时必须有解析失败兜底；无 Key 时必须有降级路径；批量生成遵守「先定答案再倒推」。
4. **前端**：不引入重型图表库，图表用内联 SVG 并做小屏适配；异步请求要防竞态（token / 元素存活检查）。
5. **隐私**：API Key 不进前端、不写明文；个人数据文件不上 Git。
6. **测试**：每条建议完成后至少新增/更新 1 条 pytest，确保：
   ```bash
   python -m pytest tests -q
   ```
   全部通过。
