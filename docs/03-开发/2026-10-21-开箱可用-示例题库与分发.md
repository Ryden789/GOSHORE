# 2026-10-21 开箱可用：内置示例题库与分发

> 配套代码：`tools/make_sample_db.py`、`app/db.py`（`seed_sample`）、`app/main.py`（lifespan）、`tools/build_desktop_exe.py`
> 配套测试：`tests/test_seed_sample.py`（8 条）

## 一、要解决的问题

exe 一直能跑，但**陌生人拿到它是一个空壳**：

- 桌面版首次启动是「题库 0 道」，什么都点不动，用户第一反应是「软件坏了」；
- `dist/` 被 `.gitignore` 忽略，GitHub 上根本下载不到 exe，只有源码；
- 手机 APK 反而开箱带全量题库（`assets/payload.zip` 249.7 MB），两端体验完全不对称。

所以「让陌生人在 5 分钟内跑起来」缺的不是代码，是**一条把成品送到人手里的路**。

## 二、示例题库：240 道真题的「试用装」

`tools/make_sample_db.py` 从全量 `content.db` 抽一份小库：

| 项 | 数量 |
|---|---|
| 真题 | 240（6 个模块 × 40 道，优先中等难度） |
| 考点 | 120 |
| 材料 | 78（含资料分析题依赖的材料，按 `material_fp` 自动带齐） |
| 时政 | 7 期 |
| 体积 | **6.92 MB** |

三个设计取舍：

1. **保留原始 doc id**。个人记录存的是 `doc_id`，重排 id 会让示例库和用户之后
   的全量导入对不上，错题本指到别的题上。
2. **只复制 `SHARED_SCHEMA` 三张表**，绝不带个人表——示例包里出现 `answers`
   会让「题库只读、可整包分发」这个边界变得可疑。
3. **资料分析必须连带材料**：只抽题不带材料，这些题在示例库里会渲染成空白。

## 三、首次运行自动垫底

`db.seed_sample()` 在 `lifespan` 里最先执行，规则只有一句：**一个库都没有时才动手**。

| 目录现状 | 行为 |
|---|---|
| 空目录（全新安装） | 复制示例库 → `data/content.db`，然后正常进 split 模式 |
| 已有 `content.db` | 不动 |
| 已有老单库 `goshor.db` | 不动（否则会变成两套布局并存 = broken） |
| 已有 `goshor.db.migrated` | 不动（迁移过但新库丢了，是真问题，塞示例会把问题盖住） |
| 打包时没带示例 | 跳过，只打印一行，不影响启动 |

复制走「先写 `.db.seeding` 再 `os.replace`」：中途失败不会留下半截 `content.db`
——半截库会被判成 split，用户看到的是残缺题库，比「没有题库」更糟。这条有测试
（`test_failed_copy_leaves_no_half_file`）。

## 四、打包与分发

`tools/build_desktop_exe.py` 检测到 `assets/content-sample.db` 就 `--add-data` 进去：

```
[i] 内置示例题库：content-sample.db（6.9 MB）
[OK] 打包完成：dist\GOSHORE上岸工作台.exe（91.9 MB）
```

exe 从 89.5 MB 长到 91.9 MB，换来「双击就有 240 道题」。

## 五、验证（实测）

## 六、修掉的一个测试隔离漏洞

真实库迁移之后，全套测试有 2 条转红。原因不是功能坏了，而是
`tests/conftest.py` 的 `_isolate_split_paths` 只 patch 了 `CONTENT_DB_PATH` /
`USER_DB_PATH`，**没 patch `DB_PATH`** —— 于是 `split_state()` 看到开发机上真实存在的
`data/goshor.db.migrated`，把所有用例都判成 `broken`。

这类「测试被开发机的真实数据影响」的漏洞比断言过期更危险：同一份代码在不同机器上
结论不同。已把 `DB_PATH` 一并 patch 到 `tmp_path`，并在 fixture 里写明为什么。
另一条 `test_split_enabled_requires_both_files` 是在断言**旧口径**（两文件都在才算
split），与「user.db 缺失＝首次运行」的新规则冲突，改写为 `test_split_state_rules`
并覆盖到 broken 分支。

## 七、发布与遗留

- **Release 已发布（v2026.10.21）**：<https://github.com/Ryden789/GOSHORE/releases/tag/v2026.10.21>，
  附件为 `GOSHORE-desktop.exe`（68,617,681 字节）与 `content-sample.db`（7,254,016 字节）。exe 仍不进仓库
  （`dist/` 被忽略），由 `.github/workflows/release.yml` 在 `windows-latest` 上构建并上传：
  Actions → Release Desktop → Run workflow，输入已存在的 tag。
- 附件名必须是 ASCII：GitHub 会静默丢弃中文，`GOSHORE上岸工作台.exe` 会变成
  `GOSHORE.exe`，因此 workflow 先复制成 `GOSHORE-desktop.exe` 再上传。
- `tools/build_desktop_exe.py` 的完成行用 `[OK]` 而不是 `✓`：Windows 控制台 GBK
  编码下 `✓` 会让 `print` 抛 `UnicodeEncodeError`，打包成功却退出 1。
- 示例库与用户导入的全量题库是**并集**（240 道示例会留在库里）。要纯全量，
  删 `data/content.db` 后重新导入即可。
