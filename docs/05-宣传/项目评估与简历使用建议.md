## 一、结论摘要

GOSHORE 是一款面向事业单位联考 C 类备考场景的个人全栈软件项目，已经超出常见的课程 CRUD 示例：它包含 FastAPI 服务、SQLite 本地数据、桌面与移动 Web 前端、Android WebView/Chaquopy 封装、题库与学习流程、数据导入导出、AI 接口、同步、测试和自动化校验。项目的优势在于功能链条较完整、场景明确、工程投入可见，作为个人作品放入简历是合适的。

当前更准确的定位是“功能较完整的个人项目/可演示原型”，还不足以描述为“生产级产品”或“已验证安全可靠的成熟软件”。最大的限制不是缺少功能，而是安全边界和验证证据：桌面服务默认对局域网开放且没有鉴权；当前富文本净化存在需要修复的 HTML 实体编码绕过可能；自定义同步加密方案需要密码学审查；本轮无法重新运行 pytest 和浏览器 E2E。项目也缺少真实目标用户的可用性测试数据。

**简历判断：可以写，且有辨识度。** 推荐投递 Python 后端、全栈开发、应用工程或测试自动化相关岗位。简历应强调完整产品流程、跨端交付和回归体系，同时准确说明这是个人项目；不要宣称生产部署、用户规模、商业效果或经过安全审计。

## 四、产品可用性、便利性与用户使用体验

### 4.1 有利于日常使用的设计

- 题库、记录和主要学习流程以本地 SQLite 为中心，降低了日常刷题对网络的依赖；AI 和 WebDAV 属于需要外部配置的能力，不能把整个产品概括成完全离线。
- 题目、错题、计划、复习、报告、辨析卡和学习统计覆盖多个备考阶段，能够形成从练习到复盘的基本闭环。
- 桌面版与移动版都存在独立页面实现，并提供 Android 包装形态；用户不必只在桌面浏览器完成所有任务。
- 当前代码已包含原生链接/按钮语义、焦点可见样式、减少动态效果偏好、空数据状态和提醒/弹窗的键盘交互处理。对应静态校验器覆盖了列表语义、窄屏设置导航、每日开门弹窗焦点等约束。
- 2026-10-07 的近期改动记录中，首页快捷入口前移、移动端 320px 设置分区换行和弹窗焦点管理均有实现与回归用例，不是只停留在优化建议。

### 4.2 对用户仍有成本的地方

- **信息量与学习成本：** 功能覆盖面很广，但新用户需要理解题库、练习模式、错题、手册、计划、AI、导入和同步之间的关系。当前代码/材料没有证明新用户能快速找到适合自己的第一条路径。
- **安装与启动：** 桌面端需要运行本地服务；Android APK 接近 300 MB。初次安装、存储占用、下载耗时和升级体验都比纯 Web 小工具更重。
- **账号与数据边界：** 软件强调本地数据，但仍有 AI 外部服务和 WebDAV 远程同步等用户主动配置的外部数据通道。产品界面需要持续说明哪些数据会离开设备、发往何处。
- **双端一致性：** 桌面和移动端各有一份较大的独立前端文件。脚本校验可防住选定的逻辑漂移，但新增功能、样式修正和无障碍调整仍要分别实现与回归。
- **尚无用户研究：** 没有任务观察、访谈、可用性量表、留存或完成率证据。可以评价现有设计覆盖面，不能据此断言“用户体验优秀”或“显著提升备考效率”。

### 4.3 当前页面与操作优化的判断

近期页面改动方向合理，优先解决入口查找、键盘可达、窄屏横向拥挤和模态焦点流失等具体问题。当前脚本能验证一部分结构、样式契约和浏览器断言，但尚不能替代用户测试，也不能证明所有页面在不同 Android 机型、字体缩放、读屏器和浏览器组合下都表现一致。

下一轮最有价值的可用性工作不是继续增加页面功能，而是找 5 到 8 名目标考生完成“首次启动并找到题目、完成一组练习、复盘错题、查看学习报告、备份数据”任务，记录卡点、误操作和完成时间。将测试结果用于调整首页路径、模块命名和帮助文案，再把高频失败步骤转成 E2E 回归场景。

## 六、需要坦诚披露的主要风险

### 6.1 局域网服务没有鉴权

`run.py` 使用 `0.0.0.0` 启动服务，README 和启动提示明确说明没有登录鉴权。同一网络的设备可以访问接口，包括数据重置、备份恢复、题库导入和设置修改等写操作。代码也给出了只在可信网络使用、不要在公共 Wi-Fi 使用的提示。

这是已知并明确记录的信任模型选择，不应写成“项目遗漏了安全提示”；但它仍然是实际安全边界。在宿舍、办公室、公共 Wi-Fi 或其他不可信局域网使用时，提示本身无法阻止其他设备调用接口。若目标是公开分发或多人长期使用，应优先改为默认仅本机监听，并为局域网访问增加认证和请求来源防护。

### 6.2 URL 抓取存在 DNS 校验与连接之间的重绑定窗口

`app/importer.py` 在请求前解析主机并拒绝私有、回环、链路本地等 IP，每次重定向也会重新检查目标；这些是相较于未校验实现的重要加固。但解析发生在 `assert_safe_url()`，后续 `httpx` 仍使用 hostname 自行连接并再次解析。若 DNS 答案在检查与连接之间变化，实际连接的 IP 可能不同于已检查的 IP。当前防护降低了直接 SSRF 风险，但还不能据此宣称完全消除了 DNS rebinding/TOCTOU 风险。

修复方向是让实际连接使用已验证的地址，同时正确保留 HTTP Host 和 HTTPS SNI/证书校验；应使用支持此类绑定的传输层方案并增加模拟 DNS 变化的回归测试。

### 6.3 富文本链接过滤缺少 HTML 字符引用解码覆盖

桌面和移动端的 `sanitizeTag()` 对 URL 做协议白名单判断，但判断发生在 HTML 解析器解码字符引用之前。例如 `href="jav&#x61;script:..."` 在净化代码看来不以 `javascript:` 开头，可能被原样保留；浏览器把结果插入 `innerHTML` 并解析属性时会将字符引用解码为 `javascript:`。若用户随后点击该链接，可能形成脚本执行路径。

现有 `tools/check_xss_sanitize.mjs` 的 94 项断言覆盖了直接的 `javascript:`、事件属性和若干危险元素，但没有覆盖十六进制/十进制字符引用、实体分隔符和浏览器解析后的 URL 协议。故本报告将其视为需要优先修复和浏览器级验证的问题，而不把现有“净化器校验通过”解释为 XSS 已完全解决。

### 6.4 WebDAV 加密属于自定义密码学设计

`app/sync_webdav.py` 使用 PBKDF2-HMAC-SHA256、SHAKE256 派生流、XOR 加密和 HMAC 认证构造自定义信封。代码描述了加密后认证和完整性检查，也有配套测试；但使用标准库实现不等同于使用经过广泛审查的标准 AEAD 算法。当前没有观察到第三方密码学审计或设计评审证据，因此宣传时应写“实现本地加密同步”，不宜写“密码学安全已验证”或“绝对安全”。

中长期应评估切换到有成熟实现的 AEAD 库，并核实 Android/Chaquopy 的依赖构建、随机数来源、密钥轮换和旧数据迁移。

## 七、简历适配建议

### 7.1 适合投递的方向

- **Python 后端：** FastAPI API、SQLite 数据模型、数据迁移、导入与备份、异步调用和错误处理。
- **全栈开发：** 独立完成后端、桌面/移动 Web 界面和端到端流程，能够说明浏览器端与服务端之间的数据边界。
- **应用工程/工具软件：** 本地优先设计、WebView/Chaquopy Android 封装、PWA 与桌面启动/安装路径。

### 7.2 简历项目描述参考

**GOSHORE 上岸题库｜个人项目**  
面向事业单位联考 C 类备考的本地化学习工作台，采用 FastAPI、SQLite、原生 JavaScript，并提供桌面 Web/PWA 与 Android WebView/Chaquopy 运行形态。

- 设计并实现题库检索、练习、错题复盘、学习计划与统计、笔记、数据导入导出及备份恢复等学习流程。

投递时应依据实际个人贡献删除不属实的表述。若时间有限，优先讲清楚一个技术难题及取舍，例如 SQLite 备份一致性、移动端异步页面竞态、双端契约校验或 Android 本地服务打包；不要只罗列几十项功能。

### 7.3 暂时不建议写进简历的说法

- “生产级/商业化/大规模用户验证”——没有部署规模、真实用户数据或可用性研究支持。
- “安全可靠/完全杜绝 XSS 和 SSRF/端到端加密已审计”——当前仍有上述安全边界与未闭合问题。
- “完全离线”——主要题库学习能力可本地运行，但 AI 和 WebDAV 需要外部服务。
- “提升学习效率 X%”或“帮助用户上岸”——没有对照实验和结果数据。
- “831 个测试本轮全部通过”——这是仓库文档记录的基线，不是本轮验证结果；而且“测试条数”不应与独立测试用例数混为一谈。

## 九、最终判断

这是一个值得放进简历的个人软件项目，优势是目标具体、系统范围真实、交付形态多、工程细节和自动化测试有材料可讲。它可以证明较强的独立实现与问题拆解能力，尤其适合初级到中级岗位面试中的项目深挖。

不过，它现在最需要的是安全边界收敛、自动化验证可复现、宣传材料口径统一和真实用户反馈，而不是继续把功能清单扩长。完成 P0/P1 项并补齐一次干净环境的全量测试后，这个项目的可信度会显著提高；在此之前，简历应按“功能较完整的个人项目”介绍，并如实披露验证范围。
