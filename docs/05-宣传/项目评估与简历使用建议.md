# GOSHORE 项目评估与简历使用建议

> 评估日期：2026-10-21（重写版）
> 评估对象：当前工作区代码、测试、构建产物与文档（`90a191e` + 本轮 E2E 隔离修复）
> 文档性质：基于实测与代码审阅的个人项目评估，不等同于第三方安全审计、性能压测或真实用户研究
> 与旧稿的关系：2026-10-07 版本是历史快照，其中「831 tests / 14 个校验器 / 无法复跑 E2E / 局域网无鉴权」等描述已经被当前代码推翻。本文按 2026-10-21 的状态重写；旧稿可在 git 历史中追溯。

## 一、结论摘要

**一句话判断：这是一个功能完整、工程化意识明显高于课程作业的个人全栈项目，适合写进简历；但它仍然是“个人项目”，不是生产级产品。**

- **可以写，且有辨识度。** 项目覆盖 FastAPI 服务、SQLite 双库、桌面/移动两套前端、Android WebView + Chaquopy、AI 能力、WebDAV 同步、打包分发和自动化回归，能支撑一场有细节的项目面试。
- **最值得讲的是“闭环”和“工程化”，不是功能数量。** 从题库导入、练习、错题、统计、计划、备份，到桌面 exe、Android APK、GitHub Release，再到 984 条 pytest、15 个前端校验器、79 项 E2E，这个链条是完整的。
- **当前最硬的短板不是代码，而是外部有效性。** 没有真实目标用户研究，没有第三方安全审计，题库来源与再分发边界需要严肃处理，E2E 尚未进入 CI，APK 仍是 300 MB 的 debug 包且未做真机验收。
- **简历定位建议：** Python 后端、全栈开发、应用工程/工具软件、测试自动化。描述时强调“独立完成 + 遇到的具体工程问题 + 如何验证”，不要用“生产级”“大规模”“安全可靠”“提升效率 X%”这类无法证明的词。

## 四、产品可用性、便利性与使用体验

### 4.1 做得好的地方

- **本地优先，学习闭环完整。** 题库、答题记录、错题、计划、统计和备份以本地 SQLite 为中心；除 AI 与 WebDAV 外，核心刷题流程不依赖网络。
- **跨端不是简单套壳。** 桌面与移动端各有页面实现，移动端针对窄屏、键盘、弹窗焦点、触控命中做了适配；Android 端还把 Python 服务嵌入 APK，属于真实的离线打包问题。
- **交互细节有积累。** 列表语义、焦点可见、减少动态效果、空状态、提醒弹窗键盘操作等都有实现和静态约束；不是只写在设计稿里。
- **数据边界比早期清楚。** P0 拆库后，题库只读、用户数据可写，备份只覆盖用户库；对“题库更新不冲掉个人记录”这类真实问题有明确设计。

### 4.2 用户仍要付出的成本

- **首次使用路径偏长。** 功能面很宽，新用户需要理解题库、练习模式、错题、手册、计划、AI、导入和同步之间的关系；目前没有证据证明用户能快速找到第一条正确路径。
- **安装体量大。** Android APK 约 300 MB，桌面 exe 约 70 MB；首次下载、安装和存储占用都明显重于普通 Web 工具。
- **外部能力需要配置。** AI 需要 API Key，WebDAV 需要服务器和口令；这部分不是“开箱即用”，宣传时应把“核心离线”和“扩展在线”分开说。
- **双端维护仍有重复。** 共享层收敛了主题、字号、目标环、搜索历史、笔记、滑动分页、草稿纸、提醒、净化和判分等纯逻辑（约 915 行），但页面编排和大量业务代码仍各写一份。
- **没有真实用户研究。** 目前只能评价“设计覆盖面”和“自动化约束”，不能评价“目标考生是否真的觉得好用”。

### 4.3 最值得做的下一步可用性工作

不要继续加功能。找 5–8 名目标考生，做一次 30–45 分钟任务测试：

1. 首次启动，找到并开始一组练习；
2. 做完后查看解析、加入错题；
3. 查看学习报告/能力雷达；
4. 新建计划或笔记；
5. 备份数据并恢复。

记录完成率、耗时、求助次数、误点位置和放弃点，把高频失败步骤转成 E2E 场景和首页/文案改动。这个证据比再加十个页面更能提升项目可信度。

## 五、当前值得保留的工程成果

1. **P0 双库拆分。** `content.db` 只读、`user.db` 可写，配 `split_state()` 的 `split`/`legacy`/`broken` 状态、迁移和备份边界；这是从“能跑”走向“可维护”的关键一步。
2. **安全边界收敛。** 默认 `127.0.0.1`，`--lan` 才开放并要求访问令牌；XSS 实体编码绕过、SSRF DNS 重绑定、Host 头校验、CORS 和 `open_app` 本地限制都已处理；新增 40 条访问控制测试。
3. **双前端共享层。** 把纯逻辑抽到 `static/shared/`，用 15 个 Node 校验器防漂移；虽然页面层仍大，但至少建立了“哪些逻辑必须一致”的契约。
4. **可重复的质量门。** 984 条 pytest、15 个静态校验器、79 项 E2E，以及 AI 33 条 golden set、内容规则校验器和抽样工具，构成了多层的验证手段。
5. **真实交付链。** PyInstaller 单文件 exe、Chaquopy APK、GitHub Actions Release、示例题库分离分发；不是只留一个 `npm run dev`。
6. **文档化复盘。** `交接文档.md` 记录了拆库、缓存版本、APK 孤儿字节、E2E 真库污染等踩坑，这些内容在面试里比“我用了什么框架”更有说服力。

## 六、需要坦诚披露的主要风险

### 6.1 题库版权与来源是最高优先级风险

`data/content.db` 约 1.2 万道真题，`assets/content-sample.db` 是 240 道示例；`LICENSE` 明确只覆盖代码，`NOTICE.md` 声明题库/内容不在 MIT 范围内。但“排除在许可证外”只解决授权声明，不解决“是否有权复制和再分发”。

此外，仓库根目录仍有 10 个未跟踪的 fenbi 抓取/提取脚本（`tools/extract_fenbi.py`、`fenbi_extract.json` 等），未纳入版本控制，但说明数据获取链路存在。对外发布、演示或写简历时，应：

- 能说明每类题目的来源、获取方式和授权依据；
- 不把题库称为“自制”或“原创”；
- 公开仓库/Release 默认只带可再分发的示例数据，不把全量真题作为卖点；
- 如无法确认授权，优先替换为公开授权题或自编题。

### 6.2 安全是“已加固”，不是“已审计”

当前已经修掉几类高价值问题：默认不暴露局域网、令牌保护写接口、XSS 实体绕过、SSRF 解析-连接 TOCTOU、DNS 重绑定 Host 绕过。这些都有回归测试。

仍需如实说明：

- `--lan` 模式是 **HTTP 明文 + 访问令牌**，同网段窃听、令牌泄漏仍是边界；只适合可信局域网。
- WebDAV 加密是自定义构造（PBKDF2 + SHAKE256 流 + XOR + HMAC），不是标准 AEAD，也没有第三方密码学评审。
- APK 是 debug 签名，没有 Play/应用商店签名链、自动更新和安全发布流程。
- 没有依赖漏洞扫描、速率限制/暴力破解测试、长稳与并发测试；不能写“安全可靠”“已杜绝 XSS/SSRF”。

### 6.3 测试证据链有缺口，且本轮发现 E2E 曾“读错库”

这是本轮评估最重要的新发现：

- P0 拆库后，`app/db.py` 的连接选择先判断 `split_enabled()`（`app/db.py:740`），再判断移动端分支；而 `scripts/e2e_mobile.py` 只重定向了移动端 `_USERS_DIR`，没有重定向全局 `CONTENT_DB_PATH`/`USER_DB_PATH`。
- 结果是：E2E 在开发机上启动移动端服务时，读到了桌面端的 `data/user.db`，带着真实的 21 条答题记录/今日 8 条，却去断言“空库初始状态”，首次运行出现 4 项失败。
- 修复方式：在 `scripts/e2e_mobile.py:128-129` 把 `_db.CONTENT_DB_PATH`、`_db.USER_DB_PATH` 指向临时库，再启动子进程；复跑 **79/79 PASS**。

这说明两件事：第一，测试套件本身也会有隔离缺陷；第二，**E2E 长期不在 CI，基线数字可能已经失效而无人发现**。当前 `build.yml` 只跑 pytest 和 15 个校验器，E2E、AI 评测、内容校验都没有自动执行；其中的 APK job 只在手动触发时尝试，且因缺 `gradlew` 默认跳过；`release.yml` 是另一条手动触发的桌面发布流程。

### 6.4 可维护性与单维护者风险

- `static/app.js` 7,033 行、`static/m/m.js` 6,597 行、`app/db.py` 4,865 行、`app/main.py` 2,903 行，阅读和修改成本高。
- 共享层只覆盖纯逻辑（约 915 行），页面编排、事件绑定和业务分支仍双份；新增功能要改两处，容易出现“桌面有、移动没有”或行为不一致。
- 项目基本由一人维护，缺少第二人 review、issue 模板、贡献指南和发布值班；这是个人项目的正常状态，但简历/面试中应承认 bus factor。

### 6.5 交付与设备验证

- APK 299.95 MB，debug 签名；本轮只做了构建、zip 完整性、内嵌前端/payload 哈希和本地 HTTP 冒烟，**没有在真机或可用模拟器上完成安装、启动、权限和离线首启验收**。
- Release 只发桌面 exe + 示例题库，不发 APK；用户要自行构建 Android 包，门槛较高。
- 没有自动更新、崩溃上报、版本回滚和安装失败指引。

### 6.6 代码规模存在多口径，对外引用容易混淆

本轮按六类扩展名实测 **148 文件 / 67,398 行**；交接文档和 docs 索引记录的是 **154 文件 / 64,865 行**，后者还包含 XML/Gradle/bat、目录范围也不同。两者不能直接相减，也不应混写成同一个“代码规模”。代码行数不是核心指标，但对外材料应统一统计脚本、扩展名、排除目录和统计日期；pytest 984、15 个校验器、79 项 E2E 的口径则已同步。

### 6.7 产品验证缺失

没有目标用户访谈、任务完成率、留存、学习效果对照，也没有真实考生对“首页该放什么”“哪种练习模式最常用”的反馈。当前所有“好用”的判断都来自作者视角和自动化约束，不能替代用户证据。

## 七、简历适配建议

### 7.1 适合投递的方向

- **Python 后端：** FastAPI、SQLite 数据建模、迁移、备份/恢复、导入、异步调用和错误处理。
- **全栈开发：** 能独立完成后端、桌面/移动 Web、Android 包装和发布链路，能讲清浏览器与服务端的数据边界。
- **应用工程/工具软件：** 本地优先、PWA、WebView/Chaquopy、PyInstaller、离线数据分发。
- **测试自动化/质量工程：** pytest、Node 契约校验、Playwright E2E、golden set 和内容规则校验；面试时主动讲“E2E 读错库”的排查过程，比只报数字更加分。

### 7.2 简历项目描述参考

**GOSHORE 上岸工作台｜个人项目**
面向事业单位联考 C 类备考的本地化学习工作台，FastAPI + SQLite + 原生 JavaScript，提供桌面 Web/PWA 与 Android WebView/Chaquopy 两种运行形态。

- 围绕 1.2 万道题库设计练习、错题、计划、统计、笔记、导入导出与备份恢复流程；将存储拆为只读 `content.db` 与可写 `user.db`，保证题库更新不覆盖个人数据。
- 建立多层回归：984 条 pytest、15 个 Node 静态契约校验、33 路由/79 项 Playwright E2E，以及 33 条 AI 输出 golden set；修复 E2E 测试库隔离缺陷，使移动端回归可重复执行。
- 完成安全加固：默认仅监听本机，局域网模式引入访问令牌；修复富文本实体编码绕过、SSRF DNS 重绑定和 Host 头绕过，补充访问控制与安全回归用例。
- 交付 PyInstaller 单文件 exe、示例题库和 GitHub Release；完成 Chaquopy Android 打包链路，处理 Python 运行时、离线资产和 300 MB 安装包等工程约束。

如果面试官追问“最大的技术难点”，优先讲一个具体问题，而不是罗列功能：

- 双库拆分后，如何保证旧库迁移、只读题库、备份和移动端单库兼容；
- SSRF 如何从“请求前检查”改成“解析一次、连接固定 IP、保留 Host/SNI”；
- E2E 为什么会读到开发库，如何用临时路径和子进程隔离修复；
- 300 MB APK 的 payload/前端/图片如何拆分、校验和压缩。

### 7.3 不建议写进简历的说法

- “生产级/商业化/大规模用户验证”——没有部署规模、SLA、真实用户数据或可用性研究。
- “安全可靠/完全杜绝 XSS 和 SSRF/加密已审计”——当前是加固和个人测试，不是第三方审计；WebDAV 还是自定义密码学。
- “完全离线”——核心刷题可离线，AI 与 WebDAV 需要外部服务。
- “提升学习效率 X%/帮助用户上岸”——没有对照实验和结果数据。
- “题库为个人原创/自制”——题库来源需要先说清楚；不能把真题库当成自己的著作权成果。
- “984 条测试全部通过，所以质量有保证”——测试通过只说明当前套件覆盖的断言通过；E2E 未进 CI、无覆盖率、AI 评测是固定样例，不能外推为“无缺陷”。

## 九、最终判断

**这是一个值得写进简历的个人软件项目。** 它的优势不是“功能多”，而是目标具体、交付链完整、工程问题真实，并且已经建立了可执行的测试与校验体系。相比 2026-10-07 的旧状态，最大的进步是：默认安全边界、双库拆分、共享层、可重复的 984/15/79 基线，以及桌面 Release。

**但它还不是生产级产品。** 最需要补的不是功能，而是：题库版权与来源、E2E/CI 的证据链、真机与真实用户验证、自定义加密的独立评审。尤其是本轮发现的 E2E 隔离缺陷说明：**自动化数字只有在正确的隔离和持续的 CI 中才可信**。

如果只能做三件事：先解决题库授权边界，再把 E2E 纳入 CI，然后找 5–8 名目标考生做一次任务测试。做完这三件，这个项目从“很强的个人作品”走向“可信的工程案例”会更有说服力。
